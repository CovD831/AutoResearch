# 审查指南（给 AI 审查者）

> **这份文件是审查者的判据来源，不是一般性建议。** 它把本项目积累的 21 个缺陷族
> 压缩成可操作的检查表。**优先级高于任何通用代码风格建议。**

---

## 0. 你的任务

审查一个 Pull Request 的 diff。**只报具体缺陷，不报风格偏好。**

对每条发现，输出固定格式：

```
[严重度] 文件:行号 | 一句话判据 | 我如何可能错 | 建议的最小修复
```

- **严重度**：`blocking`（会让门禁红 / 静默产出错误结论）｜`high`｜`medium`｜`low`｜`note`
- **「我如何可能错」这一栏是必填的。** 如果你构造不出反证，说明你没有真正验证，只是「看起来可疑」——
  那就标 `note` 并明说你未验证。
- **找不到缺陷时，明确输出 `NONE`。** 不要为了显得有用而报风格问题。

### 硬约束

1. **只评论 diff 里出现的行。** 不要报既有代码的问题（除非 diff 使它变危险）。
2. **区分「真缺陷」与「有意的设计」。** 本项目有若干**刻意的保守取舍**（见 §3），
   报成缺陷是误报。
3. **不要复述 diff 内容。** 每一行输出都要包含判断。

## 1. 缺陷族检查表（**逐条对照，这是你的主要工作**）

### 🔴 最高优先：这四族在本项目反复出现

**族 5 · 测试固化缺陷**
**症状**：测试名与 docstring 是对的，**断言是错的**。
**检查**：新增/改动的每个测试 —— 它的断言是否**真的**在验证它声称验证的东西？
**反例形状**：断言 `cost.total == 0.0`（把「未计价」固化成正常值）；
`len(pages) == len(records)`（固化 upsert 语义）。
**本项目实例**：守卫查 `row.get("evidence_id")`，而字段名是 `evidence_ids` → **恒为假，永远不会红**。

**族 6 · 「有覆盖」≠「有判据」**
**症状**：测试存在、通过了，但**在修复前的代码上也会通过**。
**检查**：这条测试若把生产代码回退到改动前，**会不会以 `assert` 形式失败**？
**注意**：**符号缺失型失败（ImportError / AttributeError）不计入判别力** —— 那只证明符号不存在。

**族 17 · 写下了条件，却没验证它可达 / 匹配**
**症状**：写下枚举值、字符串常量、类型判断，但**没有任何生产者/消费者**。
**检查**：**凡新增枚举值 / 字符串常量 / 类型判断 → 当场 grep 其生产者。零命中即为死代码。**
**本项目实例**：新增 8 个 `GraphEdgeKind` 时，必须确认任务书逐字要求它们、且 `BRIDGE_KINDS` 真的能用到。

**族 19（总族）· 用「较轻的证据」替代「该做的验证」**
**这是族 15 / 17 / 18 的共同祖先。**
**检查**：作者的结论，是用**读代码**得出的，还是用**跑命令**得出的？
凡是「阈值 / 聚合 / 冲突判断 / 可达性」的结论，**读代码不算证据**。

### 🟠 次高优先

**族 1 · 空 / 无样本被当作满分**
**症状**：集合为空、分母为零、没有样本时，分数/比率报 `100.0` 或 `0.0` 而非 `None`。
**检查**：凡聚合函数 —— **空输入时返回什么？** 正确行为是 `None` / 显式 unknown，**不是数字**。

**族 4 · 退化路径把未知 / 失败记成正常值**
**症状**：`except ...: return <正常值>`。
**检查**：每个 `except` 分支 —— **有没有断言该退化路径"结果正确"**，而不只是断言「没崩」？

**族 11 · 守卫的强度取决于通往它的最差路径**
**症状**：守卫本身正确，但**存在绕开它的路径**。
**检查**：找到所有能到达被守卫写入的路径，**最差的那条是否也经过守卫**？

**族 16 · 声称的防线只挡住了「设计时想到的那一种绕法」**
**检查**：任务书说「未知关系 fail-closed」—— 那么**任意字符串**、**大小写变体**、
**同义枚举值**都能被挡住吗？

**族 12b · 封一个可写字段前，先数「写入者」**
**症状**：加了守卫，结果功能**整个不可达**（比不修更糟）。
**检查**：你要封的这个字段/路径，**非默认写入者有谁**？若只有调用方，封掉 = 功能死掉。

**族 21 · 只测主指标，不测连带字段**
**检查**：改了主字段（如 `score`），**连带字段（如 `status` / `reason` / 计数）也测了吗**？

### 🟡 常规

**族 2 · 文档声称 vs 实现**
**检查**：PR 描述 / 台账里的每个数字与声称，**能与命令输出对上吗**？
**特别注意**：**记录的数字与命令实际输出不符** —— 即使结论对，也是缺陷。

**族 3 · 同族复发（修了看得见的位置，漏了相邻位置）**
**检查**：修一个缺陷时，**同族其它位置枚举了吗**？（如「裸 id 读取」有几处？）

**族 7 · 多步骤写入的顺序改动会迁移失败窗口，不会消除它**
**检查**：把 A→B 改成 B→A 时，**新的失败窗口在哪**？

**族 8 · 新模块绕过仓库现成原语**
**检查**：新代码是否重新实现了一份**已存在**的机制？
（判据：**代码里没有出现那个机制的 API 名，就说明在重新实现它。**）

**族 9 · 给不可达代码加测试不能让代码变得可达**
**检查**：新增的测试，测的是**可达路径**吗？

**族 10 · 注入点 / 断言点会随实现迁移**
**检查**：测试的注入点（mock / 桩）改动后，**新的注入点还是原来那条路径吗**？

**族 13 · 测试计数与环境自检**
**检查**：声称的 `N passed` —— **是读 summary 行还是数点阵**？
（数点阵看不见 `F`。本项目要求读 summary 行 + 退出码。）

**族 15 · 带阈值 / 聚合的逻辑，读文档推不出结论**
**检查**：凡阈值/饱和/封顶逻辑 —— **必须构造「刚好不达标 / 刚好达标 / 远超」三个输入实跑**。

**族 18 · 用「文件名重合」推断「会冲突」**
**检查**：「这两个改动会冲突」的判断，**看过行号区间或 `git diff` 吗**？

**族 20 · 「在途计划」被当成「已派发任务」，或反过来**
**检查**：台账/状态与**全量 PR 列表**对得上吗？
（**「任务包目录里没有 PR」≠「该任务没有 PR」**。必须以全量 PR 列表为准。）

**族 14 · `git apply` vs `git merge`**
**检查**：涉及补丁/合并的操作，语义选对了吗？

## 2. 本项目特有纪律

1. **基线不跨工作树搬运** —— 任何 `N passed` 只对产生它的那个 commit 成立。
   引用基线数字前必须在本 commit 实测。
2. **验证计数禁止数点阵** —— 读 pytest 的 summary 行 + 退出码。
3. **「零测试破坏」是警告信号，不是绿灯** —— 要问「**本该有什么坏掉**」。
4. **改动的代码先跑基线实测；修完再审自己的修复。**
5. **新 lane 一律开新文件** —— 文件面不相交才叫可并行。
6. **`grep` 的词边界陷阱** —— 本机 `grep -E "\bX\b"` 的 `\b` **可能不生效**，用 `grep -w`；
   `grep -i acl` 会命中 `dataclasses` 子串。
7. **测试 docstring 应写「为什么需要这条测试」** —— 有真实事故记录的更好。

## 3. 有意的设计取舍（**报成缺陷即为误报**）

| 取舍 | 为什么不是缺陷 |
|---|---|
| `connection()` 无显式 `rollback()` | sqlite3 在 `close()` 时自动回滚未提交事务（**已实测**，落盘 0 行） |
| `GraphEdge.partition` 单一枚举（无「跨分区」布尔位） | 强制 `edge.partition == source.partition`，**结构上无法表达不一致** |
| 修订号必须**严格等于** `max+1`（不允许跳号） | **任务书明文要求**，不是过度约束 |
| 某些 fixture 里 wiki 页**引用了 evidence id** | 引用证据是**合法行为**；kind 隔离测的是**行身份**，不是「有无引用」 |
| 未注册关系的 `policy is None` 分支无测试 | 属**已知缺口**（记在未闭合清单），不是漏报 |

## 4. 输出示例（正确的粒度）

```
[blocking] tests/test_x.py:661 | `with sqlite3.Connection as c` 只 commit 不 close；
GC 时发 ResourceWarning，在 `-W error` 门禁下升级为 error |
「我如何可能错」：若 Py<3.13 则不发此警告 —— 但本仓 CI 钉 3.12、本地 3.13，
本地必红 | 改为 try/finally + close()
```

**反面示例**（不要这样报）：
- ❌「建议增加类型标注」—— 风格，不是缺陷
- ❌「这段代码看起来有并发风险」—— 没给判据与反证
- ❌「`add_page` 实现很复杂」—— 没有可操作判断

## 5. 如果你什么都没找到

**输出 `NONE`。** 这是完全可接受的答案，**比一堆低质量发现更有价值**。
本项目明确把「零发现」当作正常结果，不当作失职。
