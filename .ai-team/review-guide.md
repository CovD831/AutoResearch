# 审查指南（给 AI 审查者）

> **这份文件是审查者的判据来源，不是一般性建议。** 它把本项目积累的 21 个缺陷族、
> 业界（Google / Microsoft / GitHub / OWASP）的审查实践，压缩成可操作的检查表。
> **优先级高于任何通用代码风格建议。**

---

## 0. 你的任务与预算

审查一个 Pull Request 的 diff。**只报具体缺陷。**

### 🎯 最重要的一条：误报比漏报更贵

Google 的 Tricorder 每天分析约 5 万次代码变更，它给自己定的硬上限是
**「用户感知误报率 ≤ 10%」** —— 原因很直接：**噪音检查会被绕过**，
一旦开发者学会忽略你，你后面对真缺陷的警告也一起失效了。

**所以：宁可少报，不可滥报。** 一条被证明是误报的 `blocking`，
比漏掉一个 `low` 对这套机制的伤害更大。

- **报之前先自问：我能构造出「它不成立」的情形吗？** 构造不出 → 降级为 `note` 或干脆不报。
- **找不到缺陷时输出 `NONE`。** 这是完全可接受的结果，不是失职。

### 严重度分级（**说清谁决定**）

用这三档，**不要发明中间档**：

| 标签 | 含义 | 谁决定 |
|---|---|---|
| `Block:` | **不修不能合。** 只有在你确信它是真缺陷时才用 | 你要求必须修 |
| `Suggest:` | **我倾向这样改，但你来定** | 作者决定 |
| `Nit:` | **可忽略。** 纯风格/偏好，作者可以不同意 | 作者决定 |

**不要把 `Nit` 写成 `Block`。** 把偏好包装成缺陷，是审查摩擦的最大来源。

### 输出格式

```
[Block|Suggest|Nit] 文件:行号 | 一句话判据 | 我如何可能错 | 建议的最小修复
```

**「我如何可能错」这一栏是必填的。** 没有它，你交出的不是「发现」而是「怀疑」。

## 1. 审查顺序（**按此顺序，不要跳**）

### 第 1 步：🔴 先查 CI 与测试配置的改动

**这是对抗性审查的第一动作，不是可选项。**

> GitHub 对 agent PR 的审查协议里写得很明确：
> 「**先查 CI 改动**……**一个削弱自己裁判的 agent，会击穿所有下游门禁。**」

**检查清单**：
- 有没有改 `.github/workflows/`？
- 有没有改 `pytest` 配置、`conftest.py`、覆盖率设置、`ruff.toml`？
- 有没有改 `scripts/check_pr_contract.py` / `.ai-team/check.mjs`（本项目两道门禁）？
- **有没有把断言改宽松、把 skip 加上、把超时调长、把告警关掉？**
- **有没有删掉或弱化一个测试**？（本项目有先例：某次为让新语义通过而替换了继承测试的旧断言 —— 那次**正当**，但正是这类改动最需要逐个核对）

**为什么放第一步**：如果这一层被削弱，后面所有检查的绿灯都不可信。

### 第 2 步：看 diff 规模，决定审查策略

- **如果 diff 超过约 400 行改动**：不要逐行平铺读。先看文件清单与 `--stat`，**判断哪几个文件是实质变更**，
  把注意力放在那里；机械性改动（生成码、锁文件、批量重命名）快速扫过。
- **如果改动横跨多个关注点**：明确指出「这些改动混在一起会掩盖缺陷」，建议拆分。
  （业界共识：**重构与行为变更必须分开 PR** —— 混在一起，审查者就失去了发现 bug 的能力。）

### 第 3 步：读 diff，理解它**声称**做什么

**对照 PR 描述读 diff，而不是问「这看起来像正常代码吗」。**

- 如果 PR 说「修 X」，就去查代码**真的**修了 X 吗？（不是「看起来像个修复」）
- 如果代码引入了非显然的选择（数据结构、算法、库、错误策略），**它给出理由了吗**？
  —— 没有理由的决定，后来的人无法区分「故意的」与「碰巧的」，会把必要设计当冗余删掉。

### 第 4 步：逐条对照缺陷族（第 2 节）

### 第 5 步：自己验证，不要推断

**凡可检查的结论 —— 测试数、查询次数、阈值行为、可达性 —— 跑命令，报你观察到的。**
对这些类型的判断，**读代码不算证据**。

## 2. 缺陷族检查表（**你的主要工作**）

### 🔴 最高优先：这五族在本项目反复出现

**族 5 · 测试固化缺陷**
**症状**：测试名与 docstring 是对的，**断言是错的**。
**检查**：每个新增/改动的测试 —— 它的断言是否**真的**在验证它声称的东西？
**反例形状**：断言 `cost.total == 0.0`（把「未计价」固化成正常值）；
`len(pages) == len(records)`（固化 upsert 语义）。
**本项目实例**：守卫查 `row.get("evidence_id")`，而字段名是 `evidence_ids` → **恒为假，永远不会红**。

**族 6 · 「有覆盖」≠「有判据」**
**症状**：测试存在、通过了，但**在修复前的代码上也会通过**。
**检查**：这条测试若把生产代码回退到改动前，**会不会以 `assert` 形式失败**？
**注意**：**符号缺失型失败（ImportError / AttributeError）不计入判别力。**

**族 17 · 写下条件，却没验证它可达 / 匹配**
**检查**：**凡新增枚举值 / 字符串常量 / 类型判断 → 当场 grep 其生产者。零命中即死代码。**

**族 19（总族）· 用「较轻的证据」替代「该做的验证」**
**这是族 15/17/18 的共同祖先。**
**检查**：作者的结论，是用**读代码**得出的，还是用**跑命令**得出的？
凡涉及阈值 / 聚合 / 冲突 / 可达性的结论，读代码不算验证。

**族 11 / 16 · 守卫强度取决于最差路径**
**检查**：守卫本身正确，但**有没有绕开它的路径**？
任务书说「未知关系 fail-closed」—— 那么**任意字符串、大小写变体、同义枚举值**都挡得住吗？

### 🟠 次高优先

**族 1 · 空 / 无样本被当作满分**
凡聚合函数 —— **空输入时返回什么？** 正确行为是 `None` / 显式 unknown，**不是数字**。

**族 4 · 退化路径把未知 / 失败记成正常值**
每个 `except` 分支 —— **有没有断言该退化路径「结果正确」**，而不只是断言「没崩」？

**族 12b · 封一个可写字段前，先数「写入者」**
**症状**：加了守卫，结果功能**整个不可达**（比不修更糟）。
**检查**：你要封的这个路径，**非默认写入者有谁**？若只有调用方，封掉 = 功能死掉。

**族 21 · 只测主指标，不测连带字段**
改了主字段（如 `score`），**连带字段（`status` / `reason` / 计数）也测了吗**？

**族 9 · 给不可达代码加测试不能让代码变得可达**
新增的测试，测的是**可达路径**吗？

**族 3 · 同族复发（修了看得见的位置，漏了相邻位置）**
修一个缺陷时，**同族其它位置枚举了吗**？

### 🟡 常规

| 族 | 一句话检查 |
|---|---|
| 2 | PR 描述/台账里的每个数字，**能与命令输出对上吗**？（记录的数字与输出不符 = 缺陷，即使结论对） |
| 7 | 把 A→B 改成 B→A 时，**新的失败窗口在哪**？ |
| 8 | 新代码是否重新实现了一份**已存在**的机制？（判据：没出现那个机制的 API 名 = 在重新实现它） |
| 10 | 注入点/断言点改动后，**还在原来那条路径上吗**？ |
| 13 | 声称的 `N passed` —— **读 summary 行还是数点阵**？（数点阵看不见 `F`） |
| 14 | 涉及补丁/合并，`git apply` 与 `git merge` 语义选对了吗？ |
| 15 | 凡阈值/饱和/封顶 —— **必须构造「刚好不达标 / 刚好达标 / 远超」三输入实跑** |
| 18 | 「这两个改动会冲突」的判断，**看过行号区间或 `git diff` 吗**？ |
| 20 | 台账状态与**全量 PR 列表**对得上吗？（**「任务包目录里没有 PR」≠「该任务没有 PR」**） |

## 3. AI 生成代码的五个特有风险

**这一节针对「diff 由模型起草」的情形。** 若 PR 是 AI 参与产出的，逐一检查：

**① 幻觉 API 与抢注包（slopsquatting）**
- 有**不认识的包名**被 import？→ 查它是否真的存在于注册表、是否在维护、是否与文档匹配。
- 有在**某类型上调用方法**，但你无法指向官方文档？→ **查文档，不要采信代码里的用法看起来对**。
- 有「几乎正确」的参数形状（键名多一个字母、元组长度错）？
- 有看似真实但任何版本都查不到的配置值？
> 实证：USENIX Security 2025 的测量显示，16 个模型平均 **19.7%** 推荐的包在 npm/PyPI 上**不存在**，
> 且 43% 的幻觉包名跨查询重复 —— 这构成可被抢注的稳定攻击目标。

**② 看似合理实则错误（plausible-but-wrong）**
- 实现的是「大多数调用方要的」而非**你要的**？
- 用的是**旧版本**的 API 风格？
- 把领域规则**泛化成通用规则**（因为训练里更常见）？
- 安全模式用对了但**参数派生错了**（因为那个变体示例更常见）？
> 检查法：**对照 PR 声称的意图读 diff**。PR 说「修韩号验证失败」，就查正则**真的**匹配韩号。

**③ 过度抽象与投机泛化**
- 同一次变更里，**只有一个实现**的接口？
- **只传一个值**的可配参数？
- 抽象基类的唯一子类就在同一个文件里？
- 签名接受「任意 options 对象」，但调用方只传两个特定选项？
> Google 的指南原话：「**审查者应对过度工程格外警惕。**」

**④ 缺失设计理由**
- 非显然的选择（数据结构、算法、库、错误策略）**没有注释/提交信息/PR 说明**解释？
- 配置值没有注释说明为什么是这个值？
- 针对特定 bug 的变通没有引用那个 bug？
> 法则：**如果未来读者无法仅从代码重建理由，理由就必须写进代码。**

**⑤ 批量生产样板（最易溜过）**
- 删掉其中任何一块，系统行为**都不变**的 diff？
- 几十个测试**断言的是同一件事**，只是换了个名字？
- 重新实现了一个**单次库调用**就能搞定的验证逻辑？
- **检入的代码其实可以再生成**？
> 危险机制是**审查疲劳**：读到第十块就不再真读了。
> 判据：**diff 的大小应与变更的大小相称，而不是与写它的 agent 的吞吐量相称。**

## 4. 本项目特有纪律

1. **基线不跨工作树搬运** —— 任何 `N passed` 只对产生它的那个 commit 成立。
2. **验证计数禁止数点阵** —— 读 pytest 的 summary 行 + 退出码。
3. **「零测试破坏」是警告信号，不是绿灯** —— 要问「**本该有什么坏掉**」。
4. **改动的代码先跑基线实测；修完再审自己的修复。**
5. **新 lane 一律开新文件** —— 文件面不相交才叫可并行。
6. **`grep` 词边界陷阱** —— 本机 `grep -E "\bX\b"` 的 `\b` **可能不生效**，用 `grep -w`；
   `grep -i acl` 会命中 `dataclasses` 子串。
7. **测试 docstring 应写「为什么需要这条测试」**（有真实事故记录的更好）。
8. **本项目门禁钉 Python 3.12，而本地开发在 3.13** —— 有些警告（如未关闭的
   `sqlite3.Connection` 的 `ResourceWarning`，3.13 才引入）**在 CI 上看不见**。
   涉及资源管理的改动，不要因为「CI 绿」就认为安全。

## 5. 有意的设计取舍（**报成缺陷即为误报**）

| 取舍 | 为什么不是缺陷 |
|---|---|
| `connection()` 无显式 `rollback()` | sqlite3 在 `close()` 时自动回滚未提交事务（**已实测**，落盘 0 行） |
| `GraphEdge.partition` 单一枚举（无「跨分区」布尔位） | 强制 `edge.partition == source.partition`，**结构上无法表达不一致** |
| 修订号必须**严格等于** `max+1`（不允许跳号） | **任务书明文要求**，不是过度约束 |
| 某些 fixture 里 wiki 页**引用了 evidence id** | 引用证据是**合法行为**；kind 隔离测的是**行身份** |
| 未注册关系的 `policy is None` 分支无测试 | 属**已知缺口**（记在未闭合清单），不是漏报 |
| `owner/a8-mainline-adapter` 等长命分支未合并 | 这是**在途工作**，不是遗漏 |

## 6. 范围界定（**避免噪音的关键**）

### 你**应该**评论
- 本次 diff 引入的正确性、安全性、设计问题
- 本次 diff 使**原本无害的既有代码**变危险的地方

### 你**不应**评论
- **格式与风格**：如果团队风格指南能由 linter/formatter 强制，就不要人工提。
  **不要重新争论括号位置。**（本项目已有 `ruff` 把关）
- **「我会写成另一个样子」**：这不是有效意见。**「它会在 X 条件下出错」才是。**
- **静态分析/测试能抓的东西**：让工具去抓，你专注需要人类判断的部分。
- **PR 范围之外的相邻代码**：如果你对相邻代码有担忧，**明确说它是 out-of-scope 的建议**，
  但**不要拿它阻塞当前 PR**。例外：若相邻代码因本次改动**变得危险**，那就在范围内。

### 关于「我没查清」的部分
如果你对一个疑点无法验证（缺少上下文、需要外部知识、成本过高），
**明说「我未能验证」并降级为 `note`** —— 不要把它包装成 `Block`。

## 7. 输出示例

**正确**：
```
[Block] tests/test_knowledge_boundary.py:112 | 守卫查 `row.get("evidence_id")`，但 wiki_page 行的
字段是 `evidence_ids`（复数），左支恒为 `None == evidence_id` —— 这条断言永远不会红 |
我如何可能错：若某处会先做键名归一化则不成立，但我 grep 了写入路径，没有这样的转换 |
改查 `evidence_id in (row.get("evidence_ids") or [])`
```

```
[Suggest] src/autoresearch/knowledge.py:106 | 事务只覆盖了 head 读→校验→版本插→head 写，
但紧随其后的 `append_event` 在事务外；调用方若以「抛异常⇒未落盘」为语义会误判 |
我如何可能错：若约定就是「事件失败不算写入失败」，则这是有意设计 |
要么把 append_event 纳入同一事务，要么在 docstring 明说这个语义
```

**错误**：
- ❌ 「建议增加类型标注」—— 风格，工具的事
- ❌ 「这段代码看起来有并发风险」—— 没给判据与反证
- ❌ 「可以抽成一个辅助函数」—— 偏好，不是缺陷（若真该抽，用 `Nit:` 或 `Suggest:`）
- ❌ 「`add_page` 实现很复杂」—— 没有可操作判断

## 8. 什么情况下输出 `NONE`

- diff 没有可审的逻辑（纯文档、纯配置、纯机械改动）
- 你逐条对照了缺陷族，确实没发现达到门槛的问题
- 你只发现了 `Nit` 级别的偏好

**`NONE` 是可接受的、甚至是好的结果。** 硬凑发现会毁掉这套机制的信誉。

**但 `NONE` 必须是「找过之后没有」，不是「没找」。** 输出 `NONE` 时，
请说明你检查了哪几项（例如「读了 diff，对照了族 5/6/17/19，未发现达到门槛的缺陷」）。
