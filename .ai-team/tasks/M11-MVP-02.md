## Goal

在 M11-MVP-01 已锁定的 Wiki+Graph 边界之上，把 `KnowledgeService.retrieve()` 内部从
「朴素子串计数 + 同分区图扩展」升级为一条**可解释、可过滤、可审计**的候选召回管线：
L0 边界过滤（`project_id` / `partition` / availability）→ L1 词法 BM25 → L2 向量召回 →
L2 同分区图扩展，每次 `retrieve` 写一条 `RecallAuditRecord` 并保证集合包含链成立。

不实现融合排序（RRF 属 MVP-03）、复杂 rerank、ContextPack 与真实领域质量结论。

## Second round — owner-approved scope extension (2026-09-17)

第一轮把管线交出来了，但四处「看起来做了」的行为经复核站不住：

1. **项目作用域没有接线**：`project_id` 是可删的实例属性，生产代码从不设置它 ⇒ L0 项目过滤
   在生产路径上从未生效，缺项目时还会被读成「所有项目」（静默放宽）。

## Boundary finding (declared, not concealed)

任务书把 L0 的 `project_id` 过滤列为必满足第 1 条（`TASK-SPECS.md:429`），但本包可写范围同时规定：

- `src/autoresearch/knowledge.py` **仅允许改 `retrieve()` 内部**（`TASK-SPECS.md:470`）；
- `retrieve()` 输入签名冻结为 `(query, *, partitions, level, limit, require_evidence)`（`:442`）；
- `src/autoresearch/application.py` 是 lane 的 `forbidden_shared_paths`（`lane-manifest.json:25`），
  `api.py` / `cli.py` 不在 `allowed_paths`。

即：`KnowledgeService` 当前没有任何项目作用域（`knowledge.py:84` 的构造函数只接 `store` 与
`relation_registry`），而本包被允许的三条路径都无法把项目传进来。**这是规格与现实的冲突，
不是实现选择**；第一轮按「能力本包交付、接线归 owner」处理（D-M11-02-01），第二轮 owner 已裁定
接线必须落在本包（见 D-M11-02-07），冲突就此关闭。

## Decisions

- **D-M11-02-01（第一轮立，第二轮改判并结案）**：项目作用域**必须是构造时输入**，且缺作用域时
  **失败关闭**。第一轮把它做成「可选实例属性 + `getattr(self, "project_id", None)`」，理由是
  不改 `__init__` / `retrieve()` 签名；第二轮复核发现该做法的后果是**静默放宽** —— 属性没设或
  被删掉时，L0 项目过滤整体失效，调用方拿到「所有项目」的结果而没有任何信号。现行做法：
  `KnowledgeService(store, *, project_id=None, embedding_provider=None, recall_audit_enabled=True)`
  （`knowledge.py:97-119`），`retrieve()` 开头 `if not self.project_id: raise
  KnowledgeScopeRequiredError(...)`（`:246-250`）。`retrieve()` 的输入签名**仍未改动**，
  所以 `:442` 的冻结条款照旧成立；`recall()` 上的显式 `project_id` 参数保留。
- **D-M11-02-02（第二轮定稿；owner 于 2026-09-18 裁定保留）**：任务书未定义「可用性」（`TASK-SPECS.md:429` 与
  `task-package.json:62` 只出现该词，仓库无定义）。冻结读法：`WikiPage.review_status` 为
  `SUPERSEDED`（`contracts.py:105-108`）的页面视为**不可用**，`published` / `draft` /
  **缺状态**（默认 draft）视为**可用**。  四格矩阵全部有测试
  （`test_the_availability_matrix_gates_the_shared_l0_boundary`），并有端到端一格
  （`test_a_published_revision_is_retrievable_and_a_superseded_one_is_not`）。
  现场核对：`contracts.py` 中 `available` / `is_active` / `archived` / `retired` / `deprecated`
  出现次数均为 **0**（`WikiPage` 唯一与状态有关的字段就是 `review_status`）。仓库里其它
  `available` 用法都在 audit lane（`audit_evidence.py:99` 的 `available`、
  `audit.py:115` 的 `full_text_available`），指的是**引文全文是否可得供核验**，与页面可用性无关，
  不能拿来当本项目过滤的锚点。若 owner 认为该词另有所指，改 `is_available()` 一处即可全量生效。
- **D-M11-02-03**：BM25 用**纯 Python、进程内**实现，不建 FTS5 虚拟表。理由：`storage.py` 是
  forbidden（无法加表/加索引），`pyproject.toml` 不在 allowed_paths（无法加依赖），而 BM25 本身
  只依赖词频与文档长度，不需要索引即可确定性复现。
- **D-M11-02-04**：向量路用**可注入的 `EmbeddingProvider`**；默认离线实现为确定性 feature
  hashing（`zlib.crc32` 分桶，不用进程随机化的内置 `hash()`），保证跨进程可复现；未注入 provider
  时向量路不可用 → 走词法回退并在 `retrieval_level` 标注降级。
- **D-M11-02-05**：不设 `channel=FUSED`。MVP-02 只做「三路候选 + 确定性重排」，融合（RRF）明确
  属于 MVP-03（`TASK-SPECS.md:495-499`、`task-package.json:87`）；`channel` 取该命中**得分来源**的
  单路通道，避免把融合语义提前塞进本包。
- **D-M11-02-06**：本包**写入** `RetrievalHit.score_breakdown` / `channel` / `matched_stage`
  （只写单路来源，不写 `FUSED`）。理由与边界声明：
  - 这三个字段**已存在于冻结契约**（`contracts.py:513-516`，R-006 C7 注入），本包不新增、不删除、
    不改名，因此不触犯 `:443`；
  - 规格把这三个字段列在 **MVP-03** 的「主要交付」里（`TASK-SPECS.md:499`，注释 `← 注入自 R-006 C7`），
    MVP-03 要做的是**融合**语义（`FUSED` 通道 + 多路 breakdown 合并）；
  - 本包**必须**写入的原因：`channel` 的契约默认值是 `LEXICAL`（`contracts.py:515`），若不写，
