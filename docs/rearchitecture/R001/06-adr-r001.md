# ADR R-001：采用薄 Runtime + Capability Adapter + 独立 Evidence Module

## 状态

Proposed，等待用户确认三项边界并通过 S1 实现证据。

## 背景

当前应用装配层和 Agent 直接依赖具体 Service/Store，难以替换用户 skill、MCP 和成熟工具；证据治理也与业务能力耦合。

## 决策

采用三层目标边界：

1. Thin Runtime：只做装配、调用、生命周期和 checkpoint。
2. Capability/Domain：通过 typed ports 接入 native、skill、MCP、plugin 和领域服务。
3. Evidence/Policy：独立保存证据事实并作确定性 Gate。

保留五个业务 Agent，但不把 Agent 作为能力扩展的唯一形式。

## 考虑过的替代方案

- 继续在现有 Service 上增加更多 connector：改动小，但耦合继续增长。
- 把每个模块都插件化：表面灵活，但没有真实消费者时会引入版本、隔离和恢复复杂度。
- 直接引入消息总线/微服务：部署和故障模型扩大，不适合当前单机 foundation。

## 后果

正面：替换能力的边界变小，证据治理可复用，旧 facade 可渐进迁移。
负面：需要维护 manifest、adapter、receipt 和兼容测试；短期代码量会上升。

## 复审条件

若两个真实 capability consumer 无法共享同一 adapter/receipt 合同，缩小抽象；若 S1 parity 失败，保留 native path 并修订 L2 合同。
