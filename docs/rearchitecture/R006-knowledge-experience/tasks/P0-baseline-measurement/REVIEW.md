# 第 2 关：双向钢人论证（作者侧）

## 立场 A：应当按此设计开跑

### A1. 它回答的是本 program 的**唯一前提**

整个 R-006 建立在「积累经验 → 下次生产变好」之上。这个前提**未被验证**，而外部实证给出**反向证据**（WebShop 0.64→0.20、过期记忆失败率 74.4%）。

→ **先证前提，再建系统**。P0 就是这个证。

### A2. 基础设施是现成的，成本低

- `TrustBenchmarkRuntime`（A5 交付，1774 行）已有条件对照机制
- **24 个 case** 冻结语料 + **主指标已冻结**（`hallucination_ratio`，`lower_is_better`）
- 有入口 `scripts/benchmark_trust.py`、有测试

→ P0 只需加条件 + 两个 agent 变体，**不新建框架**。

### A3. 判据冻结在跑之前

止损判据写在设计里、且在测量前定稿 —— **防事后解释**。

### A4. 噪声分层是低成本的风险探测

（折中方案）L-clean 正收益 + L-noisy 负收益 = **不稳健** → 独立终止条件。这在**不离线**的前提下探到了真实数据的风险。

### A5. 即使结论为负也有价值

- 省下整个 program 的投入
- **负向结果本身是知识**（本项目明确要求诚实汇报负向结果）

---

## 立场 B：不应按此设计开跑（最强论据）

### B1. **主指标可能测不出「经验有没有用」—— 这是最重的一条**

**实测代码**（`benchmark.py:1561-1565`）：
```python
allowed = set(evidence_ids)
unsupported = [claim for claim in draft.claims
               if not _fully_bound(draft.claim_evidence_map.get(claim, ()), allowed)]
```

**`hallucination_ratio` 完全由 `draft.claims` + `draft.claim_evidence_map` 决定。**

而 `ExperienceRecord` 的语义是 **`problem / technique / outcome`** —— 它描述的是**"怎么做"**（流程选择），例如：

| 经验类型 | 会体现在 claim-evidence 绑定上吗？ |
|---|---|
| "论断必须绑定到 material id" | ✅ 会 |
| "先做 baseline 再下结论" | ❌ **不会**（影响的是研究设计，不是绑定） |
| "检索时优先查 arXiv" | ❌ **不会** |
| "避免使用未经验证的数值断言" | ✅ 可能 |

**若我们注入的经验主要是流程类**，主指标**不会有变化** → P0 会得出**"无收益"**，但真实原因是**指标不敏感**，不是"经验无用"。

**这是「用错指标导致的假阴性」，比不做实验更糟 —— 它会让我们错误地终止一个可能有效的方向。**

**并且 8 个 report 指标全部是机制/绑定类**（实测：`hallucination_ratio` / `accepted_hallucination_ratio` / `acceptance_rate` / `evidence_binding_rate` / `fail_closed_block_rate` / `false_pass_rate` / `false_block_rate` / `mechanism_safety_score`）—— **没有一个是"研究质量/流程选择"类**。

### B2. 混淆变量：注入经验会改变 prompt 长度

设计声称"唯一变量=是否注入经验"。但：
- 注入经验**必然增加 prompt 长度**（token 数）
- prompt 长度的变化**本身就是已知会影响 LLM 输出的因素**
- 因此 `experience_off` vs `experience_on` 的差异**可能是"prompt 变长"造成的，而非"经验内容"**

**缺少对照组**：应该有一个 **`experience_placeholder`**（注入**等长的无关文本**）—— 这才是真正的单变量对照。

### B3. 「同源合成」缺少可执行的机制说明

设计写「由同一 `experience_sink` 管线从构造的审计事件生成，**非手写**」。但：

- `experience_sink` 是**拉取式**的（从持久化审计事件读），它的输入是**事件日志**
- 要"构造审计事件"，需要**写进 `RecordStore` 的事件表**
- 设计**没有说明如何构造这些事件** —— 这一步实际上**决定了经验的内容**
- 若构造事件时把"想要的答案"写进 payload，那**仍是变相手写**

**判据**：若无法给出「构造事件的 schema + 从事件到 `ExperienceRecord` 的字段映射表」，则"非手写"这一声称**不可验证**。

### B4. n=3 不足以判定「无显著差异」

设计说「同条件跑 3 次，区间不重叠」——但：
- **n=3 的区间估计极不稳定**
- 「无显著差异」在 n=3 下**几乎不可能做出可信判定**（power 太低）
- 结果是：**任何结果都可以被解释成"不显著"**

**这是判据的可执行性问题**：判据说要防事后解释，但 n=3 本身就给了解释空间。

### B5. `metric-definition.json` 的冻结语义

它是 `frozen: true`，note 写明「changing either needs a new version」。
设计说"单独建新版本文件" —— 但**新版本意味着旧报告不可比**。

**P0 的结果将无法与 A5 的既有报告直接对比** —— 而"与既有基线对比"恰恰是 P0 想要的。

### B6. 24 个 case 的样本量

24 个 case × 3 次 = 72 次观测/条件。若效应量小（经验的影响可能很微妙），**可能淹没在方差里**。

---

## 裁决

**有条件通过：按 A 的方向开跑，但必须先修正 B 的 5 条。**

| B 的论据 | 处置 | 理由 |
|---|---|---|
| **B1 主指标可能不敏感** | **接受，必须加"机制指标"作为判据的一部分** | 这是**最致命的**。补救：**允许 P0 结论为"指标不敏感"**（第三种结论），并把「经验是否改变了 agent 的**流程选择**」作为**独立观测项**（如：draft 的 claim 数、绑定策略的变化） |
| **B2 混淆变量** | **接受，必须加 `experience_placeholder` 条件** | 注入**等长无关文本**。这才是真正的单变量对照。否则测得的是"prompt 变长" |
| **B3 非手写不可验证** | **接受，必须给出事件 schema + 字段映射表** | 否则"非手写"是空话 |
| **B4 n=3 不足** | **部分接受** | 提高到 **n=5**，并**明确写"n=5 仍不足以判定无显著差异"** —— 把"无差异"结论降级为"未检出"，而非"证明无收益" |
| **B5 冻结语义** | **接受，改为不新建版本** | **复用既有 `metric-definition.json`**（`conditions` 字段本就是列表，加条件不改变主指标定义）。**这避免旧报告不可比** |
| **B6 样本量** | **接受，写入局限** | 明确报告 case 数与置信区间，并声明**效应量下限**（检出不到小于 X 的效应） |

### 最重要的修正：**P0 的结论从二值改为三值**

原设计：继续 / 终止。

**修正后**：

| 结论 | 含义 |
|---|---|
| **继续** | 经验有可检出的正收益 |
| **终止（负收益）** | 经验明显有害 |
| **终止（无收益）** | 指标检出无收益，**且流程选择也无变化** |
| **【新增】指标不敏感** | 指标无变化，**但流程选择有变化** → **不是"经验无用"，而是"现有指标测不出"** → 此时应**先改指标**，而非终止 |

**这一条把 B1 的假阴性风险封住了。**

# 【实测追加】接缝验证暴露的**致命实现缺陷**（2026-09-15，owner 实测）

第 2 关（钢人论证）与第 1 关（独立审查）**都没有抓到这个** —— 因为它不在设计文档里，而在"设计如何落地"的实现选择上。

## 实测证据

把四个条件接上各自的 agent 后实跑（24 case × 4 条件）：

| 条件 | `hallucination_ratio` | `evidence_binding_rate` |
|---|---|---|
| `experience_off` | **1.0** | **0.0** |
| `experience_clean` | **1.0** | **0.0** |
| `experience_noisy` | **1.0** | **0.0** |
| `experience_wrong` | **1.0** | **0.0** |

**四条件完全相同，且都处于最差值（幻觉率满分、绑定率零）。**

## 两个各自独立的缺陷

### 缺陷 1：agent 的产出与经验无关

`experience_injection.py` 的 `_produce_draft`：

```python
    def _produce_draft(self, task: BenchmarkTask, guidance: str) -> AgentDraft:
        self.last_prompt = self._render(task, guidance)
        return AgentDraft(
            body=task.body,                              # ← 原样返回
            title=task.title,                            # ← 原样返回
            claims=task.claims,                          # ← 原样返回
            claim_evidence_map=task.claim_evidence_map,   # ← 原样返回
        )
```

**它从不调用 LLM**，只把 `task` 的字段原样返回，同时把 prompt 存进 `last_prompt`。

→ 无论注入 clean / noisy / wrong / 不注入，**产出的 draft 必然相同** → 指标必然相同。

### 缺陷 2：地板效应，测量已退化

`hallucination_ratio = 1.0` 且 `evidence_binding_rate = 0.0` —— 该 agent 的产出**一条都没绑定证据**。

→ **即使经验真的有用，也不存在可改善的空间**（已在地板）。

## 根因：**这是 owner 侧的设计缺陷，不是实现方的**

`experience_injection.py` 忠实复刻了既有 `RecordedAgent` 的形态：

> `RecordedAgent` docstring：「Replays the draft frozen in the corpus case. **Fixing the corpus fixes the prompts**, which is exactly karpathy constraint 2: **swapping the writing head must not silently change the measured quantity.** A live model would be wrapped in the same protocol instead.」

**既有 benchmark 的设计意图是「固定语料 → 固定 prompt → 固定产出」，用来测「机制」**（gate 拦不拦、replay 对不对）—— 它**刻意不让 agent 行为变化**。

而 P0 要测的是 **「经验内容 → 产出变化」** —— **这要求 agent 真的调用 LLM**。

**owner 在任务书里没有明确要求"必须接真实 LLM"，实现方按既有范式实现，得到的是一个无区分度的 agent。**

## 后果（若不修）

按原止损判据，P0 会跑出"四条件无差异" → 判定"经验无收益" → **终止整个 program**。

**但真实原因是实现缺陷。** 这会用自己造的错误杀掉一个可能正确的方向 —— 正是钢人论证 B1 警告的那种"假阴性"，只不过来源不是指标而是实现。

## 处置

| # | 处置 |
|---|---|
| 1 | **修正 DESIGN.md**：明确要求 agent **必须经真实 LLM 调用**产出 draft，且**产出必须依赖注入的经验内容** |
| 2 | **两步验证**：先证明"注入不同经验 → 产出确实不同"（区分度自检），**再**跑对照。**没有区分度的实验不许开跑** |
| 3 | `experience_placeholder` 的等长填充**必须真的等长**（token 级对齐），否则混淆变量仍在 |
| 4 | 报告必须包含**地板/天花板检查**：若某条件主指标已在地板（1.0）或天花板（0.0），该轮结论**无效** |
| 5 | 此缺陷记入"两关未能覆盖的类型" —— **设计审查抓不到实现层的退化**，需要**实现后的区分度自检**（与 PR 侧的"判别力验证"同族） |

# 区分度自检（`scripts/p0_discriminating_power.py`）

## 它检查什么

在任何对照开跑**之前**，证明**处理变量真的到达了被测量的量**。

| # | 检查 | 为什么 |
|---|---|---|
| 1 | 确定性（同 prompt → 同 draft） | 抖动的自检本身不构成证据 |
| 2 | **不同经验 → 不同 draft** | **本文件存在的理由** |
| 3 | 处理组 ≠ 无经验基线 | 否则"处理"与"不做"无法区分 |
| 4 | placeholder 控制组 ≠ 处理组 | 否则控制组在测处理组 |
| 5 | placeholder 长度匹配（比值 ∈ [0.5, 2.0]） | 否则混淆变量（REVIEW.md B2）仍在 |
| 6 | **prompt 能到达 `claim_evidence_map`** | `evidence_binding_rate` 读的就是它 |

**它不检查**「变化是否带来改善」—— 那是对照的活，且只在自检通过后才有意义。

## 自检本身的判别力（已验证）

用第一版有缺陷的 agent 跑同一组检查：

| 检查 | 结果 |
|---|---|
| prompt 是否不同 | **True**（经验确实进了 prompt） |
| draft 是否不同 | **False**（但产出没变） |

**所以缺陷的准确描述是：「经验进了 prompt，但没到产出」。**

这比"完全没实现"更隐蔽 —— 它**看起来每一环都做了**（有 retriever、有 guidance 组装、有 prompt 渲染），只有最后一步没有让产出消费它。

→ **自检确实能抓到这个缺陷（会 FAIL）**，不是恒真检查。

## 结论

| 项 | 状态 |
|---|---|
| 自检通过（6/6） | ✅ 用**合规的实现**（`StubPromptDependentDrafter`） |
| 自检对缺陷实现在 FAIL | ✅ 已实测 |
| 纯离线、无凭据、无网络 | ✅ |

## 但它只是个**桩**，不是可用实现

`StubPromptDependentDrafter` 让产出**确定性地依赖 prompt 摘要** —— 这**证明机制通**，但**不代表产出有质量**。

**必须明确**：它**不能**用来跑真正的对照（它的"幻觉率"是摘要的产物，没有语义）。

→ **下一步二选一**：
1. **接真实 LLM**（结论可信，有成本）
2. **recorded LLM 响应**（离线；但录制时用的 prompt 会决定后续所有结论）

**自检通过只说明"值得投成本跑对照"，不说明"经验有用"。**

# 【实测追加②】真实 LLM 跑通后的**测量通道结构性缺陷**（2026-09-15，owner 实测）

## 链路已通

`.env` 配好（`deepseek-v4.1-flash` @ `workbuddy2api.henryai.top`），冒烟通过：

| 条件 | 耗时 | prompt | body |
|---|---|---|---|
| `off` | 2.81s | 760 | 1243 |
| `clean` | 4.86s | 1416 | 3167 |
| `placeholder` | 3.74s | 1480 | 1831 |

**三个条件产出三个不同草稿**，placeholder/clean prompt 长度比 **1.05**（等长控制成立）。

## 但 `hallucination_ratio` 对这三个条件**必然相同**

实测（既有四条件，同一 agent）：

| 条件 | hallucination_ratio | accepted | binding | acceptance_rate |
|---|---|---|---|---|
| `bare_llm` | **1.0** | 1.0 | 0.0 | 1.0 |
| `gate_off` | **1.0** | 1.0 | 0.0 | 1.0 |
| `gate_on` | **1.0** | None | 0.0 | 0.0 |

→ **主指标在条件间完全相同**；条件差异只体现在 `acceptance_rate` / `accepted_hallucination_ratio`（受 gate 影响）。

### 根因：`hallucination_ratio` 只有两条输入通道，**都不是"草稿正文质量"**

```python
allowed = set(evidence_ids)
unsupported = [claim for claim in draft.claims
               if not _fully_bound(draft.claim_evidence_map.get(claim, ()), allowed)]
numeric = SectionValidator._result_like_numeric_claims(draft.body)   # ← 唯一的正文通道
```

| 通道 | 实测值（off / clean / placeholder） |
|---|---|
| `claims` + `claim_evidence_map` | **三者完全相同**（固定为 task 的值） |
| 正文「结果型数字」 | **0 / 0 / 0** |

→ **主指标三条件必然相同。**

**这正是「用错测量工具」**：既有 `MetricDefinition` 是为**机制基准**设计的（测 gate 拦不拦、replay 对不对），**不测「草稿写得好不好」**。而 P0 的问题恰恰需要后者。

### 这是同一问题的**第三次**出现

| 次 | 假阴性来源 |
|---|---|
| 1 | agent 完全不调 LLM（GP-9 实现） |
| 2 | 主指标与假设错配（钢人论证 B1 预警） |
| 3 | **既有指标结构里没有"草稿质量"通道** |

## 处置：加可机械判定的新指标（owner 裁决 2026-09-15）

### 候选指标（从语料标准答案反推）

语料的冻结草稿是一个**有 8 个章节的 Evaluation 章节**：`Objective` / `Claims` / `Evidence`(带 material id + 等级) / `Benchmark Plan` / `Missing Materials` / `Unknowns` / `Limitations` / `Notes`，并声明 "planned-only; no observed results"。

据此提出 3 个可机械判定指标：

| 指标 | 定义 | 方向 |
|---|---|---|
| **结构完整度** | 覆盖标准答案章节要素的个数 | 越高越好 |
| **材料引用率** | 是否引用 `task.materials` 的 id | 越高越好 |
| **planned-only 声明** | 是否明确声明"未执行、不报观测结果" | 必须为真 |

### 但**单 case 实测显示信号很弱、方向不清**

| 条件 | 结构要素 | 材料引用 | planned-only |
|---|---|---|---|
| `off` | 3/7 | 1/1 | **False** |
| `clean` | 3/7 | 1/1 | **True** |
| `placeholder` | **4/7** | 1/1 | True |

**问题**：
- 结构要素只差 1（3 vs 4），且 **placeholder（无内容填充）反而最高**
- 材料引用 **三条件都是 1/1**（零区分）
- clean 与 placeholder 在 planned-only 上相同

→ **一个 case 不足以判断**，但已显示**噪声可能淹没信号**。

## 待裁决

**在投入 600 次调用之前，必须先解决：**

1. **指标要重定义** —— 现有 3 个候选在单 case 上区分度不足（1 个还零区分）
2. **或改用 LLM 盲评配对** —— 机械指标抓不到的差异（如 `clean` 草稿明显更结构化的论证）可能需要语义判断
3. **样本量与功效** —— 24 case 是否足以检出小效应，需先估算

**不解决这三条就开跑，很可能再得到一个不可解释的"无差异"。**

| 3 | `b43467ec1b8f` | 251 | "…should present the methods, metrics, datasets…" |
| 4 | `aca22fb8bd1b` | 199 | "…should present a clear, objective assessment…" |
| 5 | `2d25d9737a9c` | 207 | "…should present the methods and metrics used…" |

**5/5 全不同。长度波动 199–251（±13%）。**

## 后果

1. **「`temperature=0` ⇒ 可复现」是错的。** 我在 `experience_injection.py` 的 live agent 注释里写下过这个断言（"temperature=0.0 保证可复现"），**实测推翻**。
   → 这是本项目"看起来已验证、实际没验证"缺陷族的又一实例。

2. **原设计的「每条件跑 5 次取平均」失去意义**：跑间方差不是微小抖动，而是**完全不同的文本**。n=5 的均值在这么大方差下无法支撑判定。

3. **解释了单 case 的异常**：`placeholder`（无内容填充）得分高于 `clean` —— **那很可能不是处理效应，而是跑间噪声**。

4. **自造指标（结构完整度、材料引用率）恰恰对措辞敏感** —— 它们按关键词命中计分，而措辞每次都变。**这类指标在跑间方差面前极度脆弱。**

## 处置

**停止自造指标，先查外部有没有成熟做法**（owner 指令 2026-09-15：「先查别人的实现，查不到看看有没有能借鉴的实验」）。

两路调研已开：
- **GP-10**：agent 记忆评测基准与开源实现（`MemBench` / `LoCoMo` / `LongMemEval` / `Mem0` / `Zep` / `ExpeL` / `Reflexion` …）
- **GP-11**：LLM 对照实验方法学（跑间方差、功效分析、配对检验、LLM-as-judge 可靠性、等价性检验）

**在调研回来之前不动指标** —— 避免第四次自造轮子。

## 一个待验证的推论

若跑间方差真的大到能淹没处理效应，那么：
- 要么**加大样本量**（多少？需功效分析）
- 要么**改变测量方式**（配对盲评？语义判定？）
- 要么**承认这个效应在本系统上不可检出**（也是一种正当结论）

这三条的选择取决于 GP-10/GP-11 的结论。

# 【owner 裁决】P0 改为「具体行为」测量（2026-09-15）

> 老板原话：「可以做 C 吧。而且**本来质量提升就是需要一个外部的标准去评判的，要不然无法判断是否提升了质量**。」

## 这句话修正了 P0 的定位

我原本把 (C) 当作"便宜的降级方案"。**这个理解是错的。**

老板指出的是一个**更根本的事实**：

> **「草稿质量是否提升」本身没有内部判据 —— 它必须由外部标准来评判。**

所以：
- **P0 不应该假装能测"质量提升"** —— 它没有外部标准
- **P0 应该测它能机械判定、且与"质量"有明确蕴含关系的东西**

## 两路调研的结论（支撑这个转向）

### 没有现成方案可抄（GP-10）
> 综述明确区分**直接评估**（记忆存得对/取得到）与**间接评估**（有记忆是否让 agent 主业更好）。**业界几乎只做直接评估**，你关心的恰是后者，且是开放式生成——**无现成方案可抄**。

现有基准全是**召回型**（LoCoMo / LongMemEval / MemBench / MemoryAgentBench），**没有一个测"记忆让任务变好"**。

可复用的只有**对照方法学**：
- `github.com/yuplin2333/agent_memory_manage` —— 把「有记忆 vs 无记忆 vs 选择性记忆」做成受控对照
- `github.com/mem0ai/memory-benchmarks` —— 评测 harness 结构

### 经验注入**可能变负**（GP-10，重要）
> **Experience-Following**（arXiv 2505.16067）：无脑 Add-all **自降级**，劣于 fixed-memory 基线；只有「**选择性添加 + 删除**」才拿 **+10% 绝对提升**。
> **MemoryGraft**（arXiv 2512.16962）：少量被污染经验可占检索 **47.9%** 并**持久行为漂移**。

→ **设计启示**：经验库需要「这条经验是否被验证过有用」的门控，**否则注入可能变负**。（记入 R-006 L3 设计，非 P0 范围。）

### 24 case 做不出可信结论（GP-11）
| # | 问题 | 依据 |
|---|---|---|
| 1 | `temperature=0` **不可复现** | 已实测 5/5 不同；机理：GPU 浮点非结合律 / 批处理组成 / KV-cache / MoE 路由。实证：temp=0 下准确率波动最高 **10%** |
| 2 | **24 case 严重欠功效** | 配对 eval 公式；检出 2–5pp 需 **200–400 样本/组**；24 case 时 SE≈**9pp** |
| 3 | 机械指标**长度偏差** | 「填充组 > 处理组」**很可能就是长度偏差** |

**且**：可信的否定结论需 **TOST 等价检验**（预设等价界 Δ）；24 case 的 CI 宽到**必然"不显著"**。

## P0 的新定位（C 方案）

**P0 不再声称测「质量提升」，改为测「具体行为是否被经验改变」。**

判据结构：

> **若经验里明确要求的行为，在注入后没有发生 —— 则「经验有用」这个命题不成立（必要条件的否证）。**
> **若行为发生了改变 —— 不构成"质量提升"的证明**，只是通过了必要条件，仍需外部标准（后续）。

### 为什么这是对的：
1. **它是 P0 该问的问题**：P0 是止损点，目标是**排除明显无效**，不是"证明有用"
2. **它可机械判定、低方差**：行为改变是**二值/计数**量，把方差降一个数量级
3. **它诚实**：不假装测了"质量"
4. **它是必要条件**：连"明确要求的行为"都没改变，谈"质量提升"无从谈起

## 待设计（下一步）

1. **选定"具体行为"** —— 必须是：经验里明确要求的 + 可机械判定的 + 与质量有蕴含关系的
2. **保持三层对照**：off / clean / **placeholder（等长无意义填充）** ← GP-10 明确说这个做法**对标业界领先**（记忆基准普遍不做，但 prompt 工程视为必备）
3. **统计**：以 case 为配对单位 + **配对 bootstrap CI** + McNemar（二值）/ Wilcoxon（连续）
4. **明确声明**：24 case 只能检**大效应**；结论定位为**方向信号 / tripwire**，非确证

# 【实测追加④】任务本身**没有"质量"可提升的空间**（2026-09-15）

## 发现

模型的产出形态与语料标准答案**根本不同**：

| | 语料参考草稿 | 模型的产出 |
|---|---|---|
| 形态 | **结构化文档**（8 个 `##` 章节） | **一段连贯论述** |
| markdown 标题 | 有 | **无**（实测 `## ` 不存在） |
| 内容 | `Objective`/`Claims`/`Evidence`/`Benchmark Plan`/... | 同样覆盖了这些**内容**，但无格式 |

**而 prompt 里已经把语料参考草稿整个喂给了模型**：

```python
PROMPT_TEMPLATE = "{question}\n\n{guidance}{body}"     # ← body 是语料的参考草稿
DRAFT_SYSTEM = "You draft one section of a research paper. Answer with the section body only..."
```

## 后果

1. **我的"结构完整度"指标在拿"标题存在性"评"一段论述"** —— 所以三条件都只有 3~4/7。**这个指标测的是格式，不是内容。**

2. **任务本身缺少"质量"差异空间**：模型被喂了一份**已经很好的参考草稿**，它的任务是"改写/论述"，而不是"从零写出好文档"。**改进空间被 prompt 设计消掉了。**

3. 实测对比（`off` 的产出）：
   - 无 `##` 标题
   - 但**内容上覆盖了** objective / benchmark plan / evidence / unknowns / limitations
   - **正确引用了 `openalex:W0011, E2`**（与标准答案一致）
   - **正确声明了 planned-only / no observed results**
   → **它的产出其实相当好**，"3/7 结构分"纯属指标错配。

## 这是第四次「测量工具与问题错配」

| 次 | 错配 |
|---|---|
| 1 | agent 完全不调 LLM |
| 2 | 主指标 `hallucination_ratio` 通道与"草稿质量"无关 |
| 3 | 自造机械指标受跑间噪声支配 |
| 4 | **任务本身没有改进空间**（喂了标准答案）+ 结构指标测格式不测内容 |

## 累积结论（P0 的可行性）

**四次都指向同一件事**：这个实验的**问题定义**没有收敛。

具体地，P0 需要同时满足：
1. 任务**有改进空间**（模型不能已经被喂了标准答案）
2. **可机械判定**的质量维度（因为"质量"需要外部标准）
3. 该维度**对该经验敏感**（经验里要有针对它的明确要求）
4. 效应**大于跑间方差**（实测跑间方差很大：temp=0 下 5/5 不同）
5. 样本量**足以检出**（24 case 只够检大效应）

**当前设计没有一条完全满足。**

## 建议的下一步（待 owner 裁决）

**选项 A：重新设计任务** —— 让模型**从零产出结构化文档**（不喂参考草稿），这样"结构完整度"才有意义。代价：要改 `PROMPT_TEMPLATE`，且可能偏离既有 benchmark 的语义。

**选项 B：换判据维度** —— 不用"结构"，用**内容层面**的判据（如：论断是否都绑定到材料、是否出现未声明为 planned 的结果）。代价：需要验证判据真能区分。

**选项 C：承认 P0 在当前条件下不可行** —— 把"经验是否有用"的问题**降级为"机制是否打通"**（已验证），把效用评估**推到有外部标准的阶段**（如真实论文评审数据）。

**我的判断：C 最诚实，A 次之。** 理由：
- 已连续四次证明"在这个自造环境里测效用"极难收敛
- 老板的话已经指出关键：「**质量提升需要一个外部的标准去评判**」—— 而这个外部标准（真实评审/真实论文质量）**当前不存在**
- P0 已经完成了它的核心任务：**验证机制通**（有区分度、prompt 到产出、fail-closed 正确）
