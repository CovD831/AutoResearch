## 立场 A：应当按此 L1 执行

### A1. 方向有原始设计背书，不是我们发明的

四条决策全部落在原作者 §12–§15 的框架内。我们**没有自创架构**，只是把从未实现的设计补上。R-004 显式排除过这块（`00-scope-and-authority.md:31`），说明**当年就是分开规划的**，不是遗漏。

### A2. 断点是实测的，不是推测的

| 实测 | 数字 |
|---|---|
| `knowledge.py` | **119 行** |
| `evolution_service.py` | **117 行** |
| `profile_service.py` | **40 行** |
| 5 个 agent 调用 `knowledge.retrieve` | **0 处** |
| `graph_edge` 实际建过的边类型 | **1 种**（`summarized_by`） |

目标明确、可度量。

### A3. 外部调研支持核心判断，且揭示了原设计没说但必须做的

- 原设计的「适用/不适用边界」**有实证必要性**（`arXiv 2605.12978`：抽象剥离适用条件，WebShop 0.64→0.20）
- 原设计的 X0–X4 **比文献更完整**（ExpeL 只到投票演化、无审核/灰度/回滚）
- 调研明确说「显式适用条件可检索 + 反例抑制」**是文献未成熟处** → **我们实现它就是领先**

### A4. 四条决策都有非任意性的理由

| 决策 | 理由的性质 |
|---|---|
| 1 重写写入者 | 「不可覆盖」是**不变量**，不能做成可选字段 |
| 2 做 L1–L5+L8 | 无 L8 **无法度量**本 program 的核心目标 |
| 3 回流层用端口 | 避免越 R-004 边界，且**无端口时行为不变**（既有测试保持绿） |
| 4 页级+statement 级 | 同时满足原文 §12.2 的两句话 |

### A5. 工作量可控

四模块合计 **1077 行**（其中 `experience_sink.py` 801 行已是 A6 成果）。这是**小体量改造**，不是重写系统。

### A6. 保持了 R-004 的既有成果

决策 3 用可选端口，**不改 agent**；决策 1 只改 `knowledge` 的写入者。R-004 的 MVP 成果（509→557 passed 那条线）**不受影响**。

## 立场 B：不应按此 L1 执行（最强论据）

### B1. **决策 1 的代价可能被严重低估，且是全 program 的串行瓶颈**

实测调用点：

| 接口 | 生产 | 测试 | 合计 |
|---|---|---|---|
| `add_page` | 6 | 3 | **9** |
| `add_edge` | 1 | 2 | **3** |

**总共 12 个调用点**。而你要求「**尽可能并行开发**」——但**所有依赖 `knowledge` 的包都必须等写入者重写完成**（`evolution` / `profile` / `reader` / `search` 全在内）。

**这与"快速做完"的目标直接冲突**：决策 1 把一个**串行瓶颈**放在了最前面。

**是否有替代？** 有 —— **适配器模式**：保留 `add_page(page)` 签名，内部委托给新的 revision 写入者。这样 12 个调用点**一个都不用改**，且 revision 仍是强制的（因为唯一入口就是新写入者）。**「重写写入者」和「改所有调用点」是两件事，文档把它们绑定了。**

### B2. **「L8 必须先做」这个论断缺少论证**

文档说「无 L8 无法度量经验复用效果」。但：

- **L8 是记录召回过程**，而"经验复用是否有效"需要的是**有/无经验的对照实验**，不是召回日志
- L8 记录的是"查了什么、返回什么"，**不能回答"生产变好了吗"**

**真正需要的可能是评测框架（golden set + 对照），而 L8 只是它的输入之一。** 把 L8 说成"必须早做"是把**度量基础设施**和**度量方法**混为一谈。

### B3. **本 program 依赖三条未经我们自己验证的实证**

调研给出的是**别人的数字**（WebShop 0.64→0.20、ARC-AGI 100%→52.6%）。但这些是**通用 agent 场景**，我们的场景是**多 agent 论文生产 + 有证据门禁**：

- 我们的 `experience_sink` 是**派生 `recurrence_count`**（非累加），已经规避了部分失效模式
- 我们有 **R-004 的证据门禁**，经验本来就不能直接进论断

**"这些失效模式会发生在我们身上"是推断，不是实测。** 我们没有任何自己的数据。

### B4. **范围仍然偏大 —— 里面有四个领域，只有一个有明确断点**

| 领域 | 是否有实测断点 |
|---|---|
| 经验回流（§15 消费端） | ✅ **有**（0 个 agent 调用） |
| 知识体系（§12） | ❌ 无（revision 缺失是"设计未实现"，不是"观察到故障"） |
| 检索管线（§13 L1–L5+L8） | ❌ 无（现有 119 行能跑，没有召回失败的记录） |
| 用户画像（§14） | ❌ 无 |

**只有一个是"观察到的问题"，其余三个是"与原设计不符"。** 按"快速做完"的要求，**先把有断点的那个做完、验证有效，再决定其余三个**才是对的。

### B5. **存在"设计得很漂亮但无法验证"的部分**

- 「适用条件作为可检索字段」—— 调研明说**无成熟先例**。我们做出来后，**怎么判断它比不做更好？** 没有基线。
- 「反例抑制」—— De Neys 2003 是**人类条件推理**研究，移植到 LLM agent **没有直接证据**。
- 7 条不变量里，**I6（抽象经验保留 raw 回链）和 I7（评估集独立）无法机械校验**，只能靠约定。

### B6. **文档事实错误已经出现（本次实测抓到）**

- `add_page` 调用点：文档写 **7**，实测 **9**（含测试）
- 「7 个 agent」：实际 agent 是 **5 个**
- 「0 个专项测试」：实际有 9 个测试文件间接引用

**这些错误在被指出前都写在"决定决策的事实基础"里。** 如果独立审查不查，决策就建立在错的数字上。

## 裁决

**有条件通过：执行 A 的方向，但按 B 的意见修正三处。**

| B 的论据 | 处置 | 理由 |
|---|---|---|
| **B1 决策 1 是串行瓶颈** | **接受，改为适配器模式** | 「重写写入者」≠「改 12 个调用点」。保签名 + 内部委托，既得 revision 强制，又**消除串行瓶颈** → **直接服务于"尽可能并行"的要求** |
| **B2 L8 论证不足** | **接受，重新表述** | L8 是**度量基础设施**，不是度量方法本身。改为「做 L8 + 定义对照评测方法」，并把"度量经验复用效果"列为本 program 的**验收前提** |
| **B3 未经自己验证** | **接受，加一条前置** | 第一个包**必须先做基线测量**（我们自己的场景下，经验注入到底有没有效果），再决定后续投入 |
| **B4 范围偏大** | **部分接受** | 保持四领域覆盖（原设计完整），但**明确排序**：先做有实测断点的「经验回流」垂直切片，验证有效后再铺开 |
| **B5 无法验证** | **接受，写入风险清单** | I6/I7 标注为"约定级不变量，无法机械校验"；「适用条件可检索」标注为"领先但无基线可对比" |
| **B6 文档错误** | **已修** | 实测更正：`add_page` 9 个、`add_edge` 3 个、agent 5 个、测试覆盖澄清 |

### 最重要的修正：**B1 改变了并行可行性**

原决策 1 会让 `knowledge` 写入者重写成为**所有包的串行前置**。改为适配器模式后：

| | 原方案 | 修正后 |
|---|---|---|
| 调用点改动 | 12 处 | **0 处** |
| revision 强制性 | 强（但要求改调用点） | **强**（唯一入口即新写入者） |
| 并行性 | **差**（串行瓶颈） | **好**（其余包可在写入者就绪后并行） |

**这是本次钢人论证最有价值的产出。**

# 第 1 关：独立对抗性审查（2026-09-14）

**独立性**：子代理 prompt 不含作者推理 / 设计意图 / 怀疑点，仅给文档路径与中立问题清单，并要求**实测核实**文档声称的事实。

## 审查结论（审查者原话摘录）

> **结论**：决策方向大体合理，但 L1 在"**前提未证、I1 不可强制、既有机制未纳管**"三处存在硬伤，不建议直接定稿；应先补离线收益验证与既有代码对账。

## 三条硬伤 —— 逐条核实结果

### 硬伤 1：**I1 被我自己的引用否定**（高）— **成立，我的逻辑错误**

审查者原话：
> I1「经验不能替代事实」— 不可机械校验（最高风险）：§6.1 引 *Grounding is not a prompt* 证成"物理分离"，但**该文论点恰是"结构/RAG 无法从结构上阻止模型把上下文当事实"**——文档自引研究反而**否定**了其机制有效性。双通道只是提示结构，无代码级强制。

**核实**：属实，且是**我自己的逻辑错误**。
- `01-external-research.md:85` 我原本记为「**【关键冲突】**推理时 RAG 并不能从结构上阻止模型把上下文当事实」
- `02-l1-architecture.md:175-176` 我却用它论证「**为什么必须物理分离**」

**这是把"冲突警示"误读成"支持论据"。** 若 RAG 无法从结构上阻止，那么"放到另一个 prompt 段"**同样阻止不了**。双通道是**提示结构**，不是**代码级强制**。

### 硬伤 2：**既有机制被当绿地**（高）— **成立，规划性错误**

审查者原话：
> `evolution_service.ExperienceService` 已有 `record` + `promote` + 四门槛；`knowledge.py` 已做 lexical+graph（L1+L4）；`search_service`/`adapter_search_service`/`search_adapters` 已是独立检索层。L1 把 L3/L2/L1 当绿地。

**核实**：属实。`ExperienceService.promote` 已实现**四道门槛**：
```python
if (experience.recurrence_count < 2
    or experience.grade not in {EvidenceGrade.E2, EvidenceGrade.E3, EvidenceGrade.H3}
    or not reviewer_approved or not human_approved):
    raise PermissionError(...)
```
**这正是原设计 §15 的晋级条件** —— 已实现，我却当绿地设计。

### 硬伤 3：**决策 4 的内部张力未决**（高）— **成立，设计漏洞**

审查者原话：
> I2 要求 revision 不可覆盖，I5 要求证据失效时 statement 状态降级。当某 statement 失效：若开新 page revision，则每次状态翻转都产生 revision（写入放大）；若直接改 `statement.status`，则 statement 层可变，与 I2 精神冲突。**文档未指定二者协调方式。**

**核实**：属实，且比审查者说的更严重 ——

实测 `storage.py` 的 `put` 是 **`ON CONFLICT DO UPDATE`（upsert，就地覆盖）**：
```sql
INSERT INTO records (...) VALUES (...)
ON CONFLICT(kind, record_id) DO UPDATE SET payload_json=excluded.payload_json, ...
```

→ **I2「不可覆盖」当前在底层根本无法保证。** 我文档里"原地扩展会让 revision 退化成可选字段"的表述**不准确** —— 不改写入者的话 revision **压根不存在**。

（这**强化了决策 1 的必要性**，但**理由要改**：不是"防退化"，而是"底层就是覆盖写，必须换"。）
