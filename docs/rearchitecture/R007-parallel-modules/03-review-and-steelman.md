### 🔴 第 2 关过程中发现的**高**级缺陷（子代理与作者均未在首轮发现）

**S2：L-06 × L-07 的语义冲突 —— 经验沉淀主链路会当场崩溃**

**发现方式**：第 2 关的钢人论证要求"文件面检查必须配语义耦合检查"（B4），据此做交集检查时实测复现。

**实测证据**：

```bash
# 把 L-07 的 evolution_service.py 叠到 L-06（含 P1 的 append-only）分支上
cp wt-l2-stage/src/autoresearch/evolution_service.py /tmp/combotest/src/autoresearch/
cd /tmp/combotest && PYTHONPATH=src python /tmp/real_conflict.py
```

**输出**：
```
在 L-06（含 P1）分支上：第 1 次 record OK
第 2 次 record 失败 → ValueError: revision 1 must be > current max 1
                      for page e1 (append-only: revisions are never overwritten)
```

**根因**：
- `L-07` 的 `ExperienceService.record()` 构造 `WikiPage(...)` 时**没传 `revision`**（默认 `1`）
- `L-06` 的 `add_page` 强制 append-only：同一 `page_id` 的第二次写入必须 `revision > max`
- → **同一条经验的第二次写入直接抛异常**

**为什么这是高严重度（不是理论风险）**：

| 证据 | 说明 |
|---|---|
| `experience_sink.py:547` | **明确会重复调** `self.experiences.record(record)` |
| `experience_sink.py:755` | `recurrence_count=max(1, recurrence)` —— **"同一条经验被再次记录"正是该模块的核心场景** |
| `experience_sink.py:540-543` | 注释自己承认：「**Re-running `record` would append a second audit page for one failure**」→ 它在**绕开**重复 record，而不是修好它 |
| `evolution_service.py:116` | `WikiPage(page_id=experience.experience_id, ...)` —— **每次 `page_id` 相同** |

**→ 若 L-07 直接叠在 L-06 上，A6（经验沉淀接线）的主链路会被打断。**

## 第 2 关：双向钢人论证（作者侧）

**议题**：**L-07（M12）能否真正与 L-06（M11）并行？** —— 这是 B2 触碰的核心，也是「33 对可并行」承诺的支点。

### 立场 A：**可以并行**（应维持 33 对）

**A1. 文件面重叠只有一个文件，且重叠极浅**
实测：P2 相对 P1 在 `contracts.py` 只多 **11 行**（一个 validator）。
L-06 的 MVP-01 要改 `contracts.py` 的动机是「C1–C9 契约上收」；L-07 的动机是「`ExperienceRecord.stage` 派生」。
**两者改的是不同 class**（C1 是 `WikiPage`，L-07 是 `ExperienceRecord`）→ **git 层面可自动合并**。

**A2. 顺序已可确定，不构成双向阻塞**
P2 **已经是 P1 的超集**（实测），所以顺序天然是：**L-06 先（P1 基底）→ L-07 叠上**。
这不是"互相等待"，是"单向 stacked"。

**A3. 原计划本就把 M11/M12 放在同一波次**
原表 §3：**W6 = M11、M12、M15** 同波次 → 计划本身就认为它们可并行。

**A4. 强行串行化的代价更高**
若把 L-07 排在 L-06 之后，则：
- M12 的 P3–P7（沙箱复现/回流层/画像）全部延后
- 而 **M12-05 在原表是 5 人日、P2 已完成** → 现在是它**最容易推进的窗口**
- 延后会让已完成的 P2 长期挂在 worktree（正是 P1 昨天的处境）

### 立场 B：**不应并行**（应降为"半并行"）

**B1. 「排他文件」这个安全性论据本身是错的 —— 这是最重的一条**
L1 §5 把 `evolution_service.py`/`profile_service.py` 列为 L-07 的**「新建」排他文件**。
实测二者**已存在**且被 `reader_service.py` 等多处读取 → 它们**不是排他文件，是共享模块**。
**论据错了**，不等于结论错了 —— 但它意味着**我没有对这两个文件做交集检查**，那么"零冲突"就不是推导出来的，是假设的。

**B2. `evolution_service.py` 有真实的下游读取方**
它不是孤立模块：`reader_service.py` / `profile_service.py` 都在用它。
L-07 改它，而 L-06 要动 `knowledge.py`（`evolution_service` 的依赖）→ **存在传递影响的可能**，文档未检查。

**B3. 「33 对」的分母可能算错**
文档用 C(9,2)=36 减去 3 个串行点。但如果 L-07 真改 `evolution_service.py`，
那么**任何依赖 evolution 语义的线**都要重新审视 —— 文档只检查了文件写冲突，**没检查语义耦合**。

**B4. 前车之鉴**
本项目两次栽在"文件不重叠但语义耦合"上：S2-B 的 `audit.py` add/add、A7 与 P1 的 `knowledge.py`。
**两次都不是"文件面算错"，是"语义耦合没查"。**

### 裁决

**采纳 B1/B2 的实质（论据确实错了），但不采纳 B3/B4 的结论（并行降级）。**

| 论据 | 处置 | 理由 |
|---|---|---|
| **B1 排他文件论据错** | **接受** → **修正 §5**：`evolution_service.py`/`profile_service.py` 改标为「**修改既有共享模块**」 | 实测证实 |
| **B2 下游读取方未检查** | **接受** → **补做交集检查**（见下） | 严谨性要求 |
| **B3 分母可能错** | **部分接受** → 「33 对」改为「33 对**文件面**可并行；**语义耦合需逐线复核**」 | 措辞修正 |
| **B4 前车之鉴** | **接受为方法论** → 新增一条纪律：**文件面检查必须配语义耦合检查** | 对齐既有教训 |
| **A1–A4 结论** | **维持**：L-07 仍可与 L-06 并行，**但改为"stacked on L-06"而非"独立并行"** | P2 是 P1 超集（实测），stacked 是精确描述 |

**最终裁定**：**L-07 可与其余 8 条线并行，但对 L-06 是 stacked 关系（不是独立并行）。**
「33 对可并行」修正为：「**33 对文件面可并行；其中 L-07×L-06 为 stacked，需先 L-06 后 L-07 的提交顺序**」。
