### 3.4 收口硬检查（**2026-09-15 新增，来自一次真实事故**）

**突变一律在隔离副本里做，不得在共享 live worktree 内做。** 这是**根本约束**，
下面的扫描只是**兜底**，不能替代它。

```bash
# ① 根本检查：工作树里可能残留的、无标记的人工改动痕迹
#    （判据 = 「看起来像调试/临时短路」的形状，不依赖突变者是否留了 comment）
for wt in l01-context l02-prefetch l03-outbox l04-retraction l05-execution l08-ui l09-security; do
  echo "--- r007-$wt ---"
  grep -rnE "if (False|0):|and False\b|# *MUT|MUTATION|MUTATED|type: *ignore|# *TEMP|# *XXX|XXX:|FIXME|HACK" \
    "r007-$wt/src" "r007-$wt"/tests/test_*.py || echo "  clean"
done

# ② 正向核对：把每个 worktree 的交付态 hash 与它最后一次报告里的 hash 逐一对齐
#    成员报告应给出 sha256；hash 不等 = 工作树已偏离交付态
```

> ⚠️ **① 是启发式，必然不完备。** 一个**无任何标记**的突变（例如把 `<=` 改成 `<`、
> 把 `return early` 删掉、把 `if existing:` 改成 `if False:` 但**不写 comment**）
> 对任何基于文本模式的扫描都是**隐形的**。
> → **不要把这个扫描当作「树是干净的」的证明。** 它只能抓住「带痕迹」的那一类。
>
> **真正的完备判据只有两个**（任选其一，比扫描可靠）：
> 1. **每个 lane 在交付时把「最后一次全量绿」绑到自己的交付态 hash 上**，
>    主理人在合并前逐个核对 hash；**hash 一致 + 该 hash 上跑过全量绿 = 交付态可信**。
> 2. **突变在 `fixtures/` 下的脚本里声明，由脚本自动应用与还原**（L-05 的
>    `probe_discriminating_power.py` 是正确模式）—— 于是**工作树里不存在「突变态」**，
>    只有「可复跑的突变脚本」。
>
> → **判据 2 是本项目应当采用的规范做法**；扫描只是无法达成判据 2 时的兜底。

> **事故实证（D-2026-09-15）**：L-02 的 `invalidation.py:304` 残留了一句
> `if False:  # MUTATION M7: idempotency guard removed`，把**幂等守卫整个短路**。
> 后果链条：
> 1. **它自己的测试红了**（`test_recording_the_same_plan_twice_does_not_duplicate_audit_events`
>    → `assert 2 == 1`），而它交付报告里的「576 passed」测的是**还原前**的代码；
> 2. **残留被叠进了合并态**（L-04 的合并树 `cp` 了 L-02 的文件）→ 合并态报 `1 failed, 896 passed`；
> 3. **如果没有合并预演，这个残留会随合并进入 main。**
>
> **三条教训**：
> - **根因不是「忘了还原」，是「突变跑在共享树上」。** 突变循环在 live tree 内
>   **时序不安全**：任何人在「应用」与「还原」之间读这棵树，必然读到中间态。
>   修法是**隔离副本**（`cp -R src tests /tmp/xxx` 后在副本里突变），不是加强记忆。
> - **突变证据件应声明成 fixture 脚本**（判据 2），让「还原」变成机制而不是纪律。
> - **主理人侧**：不得在「成员还在改树」时取合并态数字 —— 见 §3.5。

### 3.5 审计与合并的时序（**2026-09-15 新增**）

**「边审边改」会让审计结论失去稳定语义。** 同一批工作需要审计时：

```
冻结（算 sha 清单）→ 审计（任何人不得写树）→ 修 → 重新冻结 → 复审
```

- **审计对象必须是「树 sha 清单」而不是目录**：目录会在审的过程中变。
- **门禁证据格式**：`树指纹 + 计数 + 命令`，例如
  `tree=<清单指纹> · 883 passed / 2 skipped / 0 failed · <命令>`。
- **审计方自检**：审计开始与结束时各算一次清单指纹并比对；不相等 → **审计自己报告「审计对象已变动」**，
  而不是靠事后看 mtime 发现。
- **主理人自检**：取合并态数字前，先确认**没有任何成员正在写树**，并跑 §3.4 的检查。

**「跑测试」不等于「改树」（2026-09-15 实测确认）**：

```
git status --porcelain | sort > before
pytest -q -o addopts="" -W error        # rc=0
node web/dev/render_contract_check.mjs  # rc=0
git status --porcelain | sort > after
diff before after                       # 完全相同
```

→ **读测试套件/门禁对工作树是只读的**：DOM 断言写 pytest 的 `tmp_path`（仓库外），
Node 守卫只读 `web/app.js` 并 `vm` 执行，产出去 stdout。
**但写盘脚本（`build_snapshots.py` / `shoot.py` / `seed_demo.py`）不在测试套件里** ——
它们**要显式手跑**才会写 `screenshots/` 或 `var/`（后者已被 `.gitignore` 命中）。

**推论（对冻结窗口有用）**：冻结期间若**仍见树在动**，来源**不是**测试套件，
只会是**有人手跑了写盘脚本**。→ 冻结窗口的检查应针对**写盘脚本**，而不是普通 `pytest` 运行。

> **事故实证**：证伪官审计期间，主理人同时派了另一个成员修 D1 —— 它读到的
> `retraction.py` 是 337 行、交付后变 498 行，计数从 876 漂到 883。
> **「876 / 2」这个门禁证据无法从当前树重新导出**，已作废。

> **另一起（同一根因）**：主理人在合并预演时用了尚未还原残留的树，
> 报出 `1 failed, 896 passed`。**两次事故的共同点是「树在动的时候取了数字」。**

## 3.6 Gate 条款：环境依赖的证据（**2026-09-15 新增**）

> **来源**：审计发现一处**结构性盲区** —— 两个数字在门禁看来完全一样，但实际保护不同。

**条款**：**凡「修复的证据只在特定环境可跑」的，必须在无该环境时也有一条可执行的替代断言，否则按未验证计。**

**事故实证**：L-08 的渲染层修复（tab 状态点）依赖 Playwright/Chrome 的 DOM 断言。
实测等价硬编码突变下：

| 环境 | 门禁看到 | 实际保护 |
|---|---|---|
| 有浏览器 | `897 passed / 2 skipped / 0 failed` | 完整（1 failed 会红） |
| **无浏览器** | **`895 passed / 4 skipped / 0 failed`** | **少 2 条判据 —— 突变完全没被抓到** |

**两个数字在门禁看来都是「全绿」。** 即「绿」这个信号里**混入了环境信息，而门禁不知道**。

**配套要求（两条）**：

1. **门禁信号必须显式带 `skipped 数` + 关键可选依赖的可用性** ——
   `passed / skipped / failed` 三元组**无法区分**「真的都跑了」与「一部分被跳过了」。
2. **必须有「无该环境」的替代断言**。正面范例（L-08 的 `web/dev/render_contract_check.mjs`）：
   **用最小 DOM stub 执行真实的 `web/app.js`、只用 Node（项目硬需求）、断言可观测 class 而非源码形状。**
   该模式可复用到任何「只有浏览器能验」的断言上。

## 3.7 Gate 条款：突变/注入的有效性（**2026-09-15 新增**）

**条款**：**突变本身必须先证明它改变了行为**，否则 `MISSED` 可能只是突变没生效。

**两处独立实证**：
- **L-08**：它写 N1 突变时改成了**新增一个未被调用的函数** → 跑出 `MISSED`，
  **差点据此得出「守卫漏了」的错误结论**。那是突变没生效，不是缺口。
- **L-02**：改用新 API 后，原先 monkeypatch 旧方法的失败注入**静默失效**
  （脚本仍报 PASS 但什么都没注入）。

**要求**：突变后必须确认「旧路径已不可达 / 行为真的变了」。
**否则两个方向的错误都会发生** —— 既有「把没生效的突变当成缺口」，也有
「把没生效的突变当成已抓住」。

**复用一个曾被突变的副本前，必须先确认它已还原**（2026-09-15 新增）：

```bash
# 验收/复跑前的前置检查（缺一不可）
shasum -a 256 <副本路径>/<被突变文件>     # 必须 == 权威清单里的值
cd <副本路径> && shasum -a 256 -c <权威清单> | grep -c FAILED   # 必须 == 0
```

**`restore` 不得依赖「脚本能跑到底」**（2026-09-15 新增）：

> **长批量脚本被 SIGTERM / 超时中断时，尾部的 `restore` 不会执行。**

**要求（三选一或组合）**：
1. **每个突变独立一次运行**（强制分开，不串跑）—— **首选**；
2. 用 `trap ... EXIT` 兜住还原，使中断路径也执行；
3. 还原后**必须核 hash** —— **不只看脚本有无报错**（脚本可能根本没跑到那一步）。

> **事故实证**：L-02 把 4 次全量验收串在一条命令里（约 2 分钟）→ 被 SIGTERM 中断（退出码 137）
> → **中断点之后的 `restore` 没执行**，副本短暂停留在注入版本。
> 它立即从备份还原、核验 hash MATCH、`grep` 确认 0 残留、并把该变体**单独重跑**取证。
> **处置全对，但风险是结构性的** —— 它自己指出：「多次全量串跑超时这个形态本身
> 会让 `restore` 变成『不保证执行』」。

> **突变纪律的完整演进链**（每一层都是被一次真实事故逼出来的）：
> 1. 「突变后要还原」← 我最初的约定（**不够**）
> 2. 「突变跑在共享 live 树上**时序不安全**」→ **必须隔离副本**
> 3. 「复用曾被突变的副本前**必须先验签**」→ 防拿污染树当干净基线
> 4. 「`restore` **不能放在可能被中断的脚本尾部**」→ 本条

> **事故实证**：主理人原本打算**直接复用**对抗性审计遗留的副本
> （`/tmp/falsify-r007/xtest`）做第五次验收 —— 而那个副本当时**含刚施加的跨模块写入突变**。
> 若不复核就直接用，第五次验收会在**一棵已被污染的树**上跑，pass 之后所有结论都无效。
>
> **审计方做得对的地方**：它没有停在「我还原了」，而是**写了一条防复用错误的前置条件**
> （「验收前必须确认 `X-1 == X-0` 且验签 `0 FAILED`，否则可能拿含绕过的树当干净基线」）。
> **这是「突变必须在隔离副本里做」的下一步**：隔离解决了「不污染 live 树」，
> **但没解决「副本本身被复用时的状态」**。

## 3.8 守卫的覆盖面必须诚实声明（**2026-09-15 新增**）

**本项目反复出现「守卫看起来比实际强」**，同型**四处**：

| # | 守卫 | 实际覆盖面 | 被谁打穿 |
|---|---|---|---|
| 1 | `isinstance(x, Protocol)`（`runtime_checkable`） | **只查方法名，不查签名** | D1：裸 service 绿灯，首次调用才 `TypeError` |
| 2 | AST「唯一写入点」 | **只认字面语法形状** | R3：`getattr(self.store, "put")(...)` 完全隐身，全量仍绿 |
| 3 | 前端三条源级守卫 | **按字面量取指纹** | R4：等价改写（`cls \|\| "…"`）全部为绿 |
| 4 | `data-dot-state` 断言 | **渲染器自己写的属性（循环证据）** | R6：点与 chip 已矛盾时仍通过 |

**要求**：
- **优先在行为上设判据，而不是在语法形状上取指纹**（R3 的修法：给 `store.put` 打桩计数）。
- **凡守卫的覆盖面小于其外观的，必须在 L3 写明边界**，不得让它看起来比实际强。
- **L-02 的自评值得作为范例**：它写下的「已知局限：kind 走变量赋值会漏报」
  **方向对但范围写小了、且从未测试过** —— 它自己承认**这是把未验证的断言当结论**，
  正是本项目要防的缺陷族。**局限声明本身也要有证据。**

### 3.8.1 「唯一写入点」三层机制的真实覆盖面（**实测，2026-09-15**）

> 这条是 §3.8 的样板案例：**一个不变量被三个机制分别守护，而没有任何单个机制覆盖全部。**

| 机制 | 覆盖 | **不覆盖** |
|---|---|---|
| **AST / 字面量守卫**（原状） | 只有**字面调用点** | `getattr` / 别名 / 变量 kind / **跨模块** |
| **运行期守卫**（L-02 patch：`store.put` 打桩计数 + 不加 partition 过滤的落库条数） | **调用作用域内**的所有 `store.put`（任意 handle、任意 kind，含 `getattr` 与别名） | **调用作用域之外**的写入（**含其它模块**） |
| **权威清单验签** | **所有被清单覆盖的文件**的任意改动 | 不在清单内的文件（`.github/**`、`.gitignore`、`var/` 等） |

**关键实测**（对抗性审计 Q3）：
`PREFETCH_RECORD_KIND` 的写入被插到**另一个模块**（`context_assembler.py` 的
`HandoffReplayService.by_run`，该路径**被 m01 测试真实执行**）→

```
AST 守卫            1 passed                                  ← 盲
m01+m02+web_panels  76 passed                                  ← 盲
全量                906 passed / 2 skipped / 0 failed          ← 零检出
```

且该写入**发生在任何 `execute_l2_action` 之外** → **运行期守卫同样会漏**。

**→ 已知边界（三条，全部实测，不得声称已覆盖）**：
1. 未被走到的分支里藏写入
2. 别的 kind + 别的 handle
3. **任何 `execute_l2_action` 作用域之外的写入（含其它模块）**

**要求**：**任何「不变量已被守护」的声称，必须指明是哪个机制、覆盖到哪一层。**
写「已守护」而不指明层级 = 高估覆盖面。

> **附带教训（可重演性）**：宣称「补丁已实测 N 种绕过全部开火」时，
> **验收必须重新施加那 N 种绕过** —— 只跑聚焦测试只能证明「补丁没弄坏这个文件」，
> **证明不了判别力**。不可重演的实测 = 口述。

## 4. 三条纪律（各对应一次真实事故，**开工前重读一遍**）

1. **文件面检查必须配语义耦合检查。**

3. **裸露的「未测/缺失」绝不许记成正常值。**
   凡 `except ...: return <正常值>` 处，必须有断言该退化路径**结果正确**的测试，
