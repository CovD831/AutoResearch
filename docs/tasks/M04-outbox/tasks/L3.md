## 3. Implemented design

### 3.1 三层职责（互不越权）

| 载体 | 担当 | 不加新表 |
|---|---|---|
| `records` kind `outbox` | K9 条目本体（`status` / `attempts` / `delivered_at`） | ✅ 用既有 `records` 表 |
| `records` kind `outbox_payload` | payload 本体（**K9-2**：条目只存引用） | ✅ |
| `records` kind `outbox_schema` | schema version + 迁移失败审计 | ✅ |
| `idempotency` scope `outbox` | **K9-1** 副作用身份：key 原样作 `idempotency_key` ⇒ 唯一约束即契约要求的唯一约束 | ✅ 既有表 |
| `idempotency` scope `outbox_attempt` | **K9-3** 每槽一行（`{key}#a{n}`），**槽位抢占 = 既有唯一约束**；`state`/`phase` 即 A1/A2 词表 | ✅ |

`attempts` 是**派生值**（= 已占槽位数），不是自增计数器。理由同 A6 的 D-A6-02：崩在「副作用已发生、计数器未写」之间时，派生值不会丢预算。实测覆盖：`test_attempts_is_derived_from_the_durable_attempt_rows`（把条目上的计数清零，预算仍精确）。

### 3.2 `deliver` 的判定顺序（K9-1 / K9-3 / I7 的落点）

```
1  entry = entry(outbox_id)                       # 不存在 → KeyError
2  _resolve_existing(entry)                       # 不开槽：重复投递在这里就被拒
     ├ effect marker finalized+delivered  → replayed（不跑副作用）      ← K9-1
     ├ latest attempt finalized+delivered → replayed                     ← K9-1
     ├ latest attempt finalized+未送达     → 放行（确定失败，可重试）        ← K9-3
     ├ latest attempt pending@service_returned → 收口 staged，不重跑     ← I7 恢复
     └ latest attempt pending@service_started  → UNKNOWN，fail-closed     ← I7 安全面
3  attempt = _claim_attempt(entry)                # reserve_idempotent 原子抢槽
     └ None → _spend_budget（仅当整本槽账都终局才写 failed）
4  _resolve_existing(entry, claimed_attempt=…)    # 抢槽后复查：关掉「检查—使用」窗口
5  _run_attempt：reserve 身份 → mark service_started → 解引用 payload → 跑 effector
     ├ 成功 → mark service_returned → finalize 槽位 + finalize 身份 → DELIVERED
     └ 抛异常 → finalize 槽位(delivered=False)；预算尽则 FAILED，否则 PENDING
```

### 3.3 两类失败的**语义分界**（明示，不是静默假设）

| 现场 | 判据 | 处置 |
|---|---|---|
| `pending@service_started` 且没有活着的 worker（进程死亡 / 崩溃） | **UNKNOWN**：副作用**可能已发生** | **不重跑**，`status=failed` + `reason="unknown outcome…"`，由 `resolve_unknown` 显式收口 |
| `pending@service_returned`（副作用已发生，只丢了记账） | 已发生 | 收口 `staged_result`，**不重跑**（I7） |
| effector 抛异常 | 本次尝试**确定未确认** | 消耗槽位、有界重试（K9-3 的存在理由） |

> 边界声明：本包把「effector 抛异常」理解为「本次尝试未确认」，因此允许有界重试。
> 若下游副作用可能在抛异常**之前**已发生，调用方必须让 effector 自身按 `idempotency_key` 幂等，或改走 `resolve_unknown`。
> 这是**明确的语义边界**，不是静默假设。

### 3.4 M04-06：迁移

- **空库**：无条目 → 只写 version record（`migrated=0`）。
- **旧库**：`_normalize_entry_payload` 把旧形状映射到当前形状（`sent→delivered`、`error→failed`、补 `attempts=0`/`delivered_at=None`）。
  **读不懂的行（缺 `outbox_id`/`idempotency_key`/`effect_kind`/`payload_ref`）不猜测**：计入 `skipped` 并给诊断，行**原样保留**。
- **部分失败可回滚**：全部重写 + version record 在**同一个 `transaction()`** 内；异常 → 隐式事务回滚 → 版本号、条目均不变。
- **回滚后仍可审计**：在事务**之外**写 `outbox_schema/migration_failure`（含 `from_version` / `attempted_version` / `reason` / `failed_at`），`migration_failure()` 可读。
- **前向不兼容拒动**：库版本 > `SCHEMA_VERSION` → `refused=True`，零写入。
- **version record 不可解析**（如 `{"version": "one"}`）→ 抛 `OutboxSchemaError`，**不降级为 0**（「缺失」与「读不懂」不得塌成同一个值）。

### 6.3 判别力**实测**（反向验证，不是声明）

**(a) 反向控制（judgement-type，在测试套件内常驻）**
`test_counterfactual_a_ledger_free_outbox_duplicates_the_effect`：同一场景、同一插桩，但换成一个「把预算与送达标记放在条目上、自己做 read-modify-write」的对照实现 `_LedgerFreeOutbox`。
实测结果：**对照产生 2 条外部副作用**，而生产实现产生 1 条。
→ 若生产断言 `sink.count() == 1` 是空洞的，这条对照会报 1 而不是 2。**对照已绿 → 生产断言非空洞。**

**(b) 反向控制（lost-update，在测试套件内常驻）**
`test_counterfactual_read_modify_write_counter_loses_an_increment`：同一 `_Gate` 下跑朴素的「读计数 → 写计数 +1」，实测 `observed == [1, 1]`（**丢了一次增量**），而生产 `_claim_attempt` 在同一插桩下得 `[1, 2]`。这就是「必须走 `reserve_idempotent`」的直接判据。

**(c) 把生产实现换成朴素版（临时副本，`/tmp`，未进仓库）**
把 `outbox.py` 的 `_claim_attempt` 换成「读 `_attempts()` 后 `return used + 1`（不抢占）」的朴素版，`PYTHONPATH` 指向该副本重跑本套件：

**失败类型诚实说明：全部是「符号缺失型」**（`KeyError: unknown idempotency record: outbox_attempt:key-1#a1`），

所以 (c) 只证明「套件对该机制敏感」，**不**证明「套件能抓住静默重复副作用」；

## 8. 已知边界与遗留（**负向结论优先**）

1. **本包没有生产触发通路**（最大缺口）。`outbox.py` 目前只被测试引用：没有 `Application` 方法、没有 HTTP 端点、没有 CLI 子命令。原因：`application.py` / `api.py` / `cli.py` 均**不在本 lane 排他清单**（L-08 拥有 `api.py`）。A6 的教训（第 4 条交付物）说明「接线了但生产永不触发」是真实失效模式，故此处**明报**：本包交付的是**引擎**，接线需 owner 指派（建议单开一条接线包，或并入 L-08）。
2. **条目 `status` 在并发下是 last-writer-wins**（D-L03-07）。已缓解（败者不轻易写标签），但极小窗口内 `status` 可能与槽账不一致。**权限在 `idempotency` 行**，故不会导致副作用重跑；影响限于观测精度。
3. **`_claim_attempt` / `_finalize_attempt` 依赖 `Storage` 的固定转移表**：`mark_idempotent_phase` 只允许 `reserved → service_started → service_returned`。若上游把转移表收紧/改名，本模块会红（不是静默错）。同理 `finalize_idempotent` **不幂等**（已 finalized 会抛），本模块靠「先复查 + 容忍 `already finalized`」兜住 —— 这依赖**错误消息文本**匹配 `"already finalized"`，属脆弱点，登记在案。
4. **effector 抛异常 ⇒ 允许有界重试**（§3.3 的边界声明）。若下游副作用可能在抛异常前已发生，本包**不**能替调用方判断 —— 必须由 effector 自身幂等或由 owner 改判（D-L03-06）。
5. **`attempts` 派生自槽账，上界 = `max_attempts`**：若日后再调小 `max_attempts`，**超出新上界的旧槽位行将不可见**（`_attempts` 只点查 `1..max_attempts`）。已在 `_latest_attempt` / `_attempts` 处如实反映；改小配置属运维动作，需 owner 知晓。
6. **`service_started` 的「在飞」与「已崩」不可区分**（durable state 相同）→ 一律 fail-closed。代价：一次瞬时的并发撞车会要求 `resolve_unknown` 显式放行，**不会自动重试**。这是有意的安全取舍。
7. **迁移只覆盖 outbox 自己的 schema 版本**，不含 `storage.py` 的表结构迁移（那需改串行点，超出本包文件面）。
8. **迁移的行顺序未保证**：`store.list()` 按 `created_at, record_id` 返回；失败注入测试依赖的 `outbox_old1/2/3` 顺序由 `created_at` 决定（fixture 里递增），非通用保证。
