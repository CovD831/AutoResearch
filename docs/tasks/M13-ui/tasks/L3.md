## 2. Implemented design

交付物本体在代码里（`src/autoresearch/web_api.py`、`web/`），本节只记决策。

### 2.1 分层

```
web/index.html · styles.css · app.js     原生 HTML/CSS/JS，无框架、无构建
        │  GET /ui/panels/{panel_id}?project_id=...
        ▼
src/autoresearch/web_api.py              ← 本包唯一新增后端文件
    ├─ K14 类型：PanelSection / PanelProjection（pydantic，带不变量校验）
    ├─ 纯函数 builder：build_panel(panel_id, PanelSources) -> PanelProjection
    └─ PanelReader：只读采集 5 个 GET 端点 → PanelSources
        │  只读调用与 api.py 同源的 service accessor
        ▼
既有 24 端点（/api/* 由 create_web_api 重新挂载，写操作走它们）
```

* **`web_api.py` 是 BFF，但不是新的数据源**：它只调 `api.py` 已经在用的同一批
  只读 accessor（`projects.get` / `get_run` / `evidence.list` /
  `execution.list_work_packages` / `store.events`），
  **AST 级证明它没有任何变更态调用点**（§6）。
* **不改后端**：`src/autoresearch/` 既有模块**一个字节都没改**（`git status` 可证）；
  新增文件落在本 lane 排他清单内。
* **写操作仍走既有端点**：`app.js` 直接 `POST /api/runs/{id}/resume` 与
  `POST /api/evidence/{id}/invalidate`，**不经过 BFF**，因此不存在「面板绕过端点写状态」。

### 2.2 项目 → run 的解析链（G-2 的绕法，且对读者可见）

`resolve_run_id(sources) -> (run_id, resolution)`：

1. `sources.run` 有 `run_id` → `"run-payload"`
2. 否则倒序扫审计日志找 `run.started`，取其 payload 的 `run_id` → `"audit:run.started"`
3. 都没有 → `(None, "unresolved")`

`resolution` 会作为 `run_resolution` fact 出现在面板上，所以**读者能看见这一跳怎么来的**，
而不是面板偷偷猜。

### 2.3 三态语义（**这是 K14-1 的落地**）

| 状态 | 判据 | `verified` | `unknown_reason` |
|---|---|---|---|
| `verified` | 该 section 的内容**已从某个真实端点读到**，且引用的 id 全部解析 | `True` | 必须为 `None` |
| `unverified` | 数据**缺失/无法读取**：端点不可用、字段为空、字段不存在、无读取模型 | `False` | **必须非空**，且必须说清缺什么、为什么 |
| `blocked` | **上游依赖阻塞**：`run_status∈{blocked,failed,interrupted}` / `lifecycle∈{waiting_evidence,waiting_human,rejected,failed}` / 有 `status=blocked` 的工作包 / 依赖未交付 | `False` | **必须非空**，装的是真实 blocker 文本 |

* 面板级状态 = **最坏 section 状态**（有 blocked 则 blocked；否则有 unverified 则 unverified；否则 verified）。
* `refs` 空 + `sections` 为空的面板**禁止构造**（`min_length=1`）——
  空面板会读成「一切正常」，正是 K14-1 要挡的。

### 2.4 「空缺」与「读了但为空」是**不同的两个事实**

`PanelSources` 里 `None` = 该端点读不到；`[]` = 端点答了、列表就是空的。
两者走**不同**的 reason 文案，并有专门测试（`test_N1_none_and_empty_are_different_facts`）。

### 2.5 各面板 section 清单

**project（M13-04）**：阶段 / Gate 裁决 / 证据覆盖 / handoff / 任务 / 阻塞 —— 6 个。

**evidence（M13-05）**：证据项 / 按 claim 归类 / 按 run·action 归属 / Gate 裁决 /
审查与裁决 / 评审报告 / 回退入口 —— 7 个。

**approval（M13-07）**：审批范围 / 风险等级 / 支撑证据 / 待人工决策 / 审批历史 —— 5 个。

**files（M13-06）**：1 个，`blocked`（理由写明依赖 K11）。

### 2.6 M13-07 的写侧映射（**实测**，不是设计意图）

| 交互 | 端点 | 证据 |
|---|---|---|
| 确认 / 拒绝 | `POST /runs/{run_id}/resume` body `{approval, reviewer, note}` | 实跑返回 **409** `run is not waiting for a human interrupt`（本包无 pending interrupt，见 §8） |
| 打回 | `POST /evidence/{evidence_id}/invalidate` body `{reason, actor}` | 实跑返回 **200**，审计新增 `evidence.invalidated`（actor=`l08-demo`） |

**审批可归因性（实测，推翻了先验假设）**：我原本以为 approve 只写
`run.checkpointed`（actor=`application`）因而**无法归因到人**。读 `graph.py` 后发现：

* approve → `graph.py:132` 写一条 `evidence_type=human` / `grade=H3` /
  `source_id=<run_id>` 的证据，`actor=<reviewer 名>`；
* reject → `graph.py:103` 以 `explicitly_rejected=True` 走 gate，落一条
  `gate.evaluated`（`operation=external_manuscript_release`）。

因此审批历史**能**归因，且面板真的把它标成了 `verified`（截图
`litalpha-approval.png` 的 `actors=l08-demo`）。判据 `_is_human_decision()`
带 docstring 写明三个判据与**已知局限**（见 §8）。

### 2.7 K14-2 的强读法，与 D-L08-04 的保守取舍

**强读法**：`refs` 只放不透明标识符；**正文类内容一律不进投影** ——
证据 `claim`/`title`、wiki `body`、稿件正文、gate `reasons`、
review `findings`、审批 `message` 全部留在原 store，面板只带**能解析到它们的引用**。

落地：
* `refs` 有正则约束（`REF_PATTERN`），带空格的句子**根本构造不出来**；
* `facts` 只放有界标量（key 是机器名，value ≤200 字符且单行）；
* N-3 测试用**真实证据的 claim/title 全文**做子串断言。

**D-L08-04（保守取舍，已获 team-lead 裁决维持）**：审批面板因此**不渲染**
`interrupt.message`（那句「请先读再决定」的提示语），只给
`message_ref = GET /runs/{run_id} -> interrupts[0].message`。

要点（避免下一个读者误读）：

* **这不是契约要求，是我的保守选择。** `interrupt.message` 是**运行时的审批请求文本**，
  不是**库里的正文**，它不承载「已证实 / 未证实」的语义判断，
  因此 **A5 的本意并不禁止**它出现在面板上。
  我按 K14-2 的**字面**实现（正文类内容不进投影），代价是审批面板比
  「什么都能看」的版本**更难用**。
* **信息没丢**：`message_ref` 指向唯一权威来源，读者可点开。
* **属于取舍而非正确性**：在无明确授权时保守是对的；
  若 owner 要求更佳可用性，**回退一行**（把 message 放进 `facts` 即可）。

## 3. Deliberate non-goals

* **不做 M13-06**（ACL 导出），只把它渲染成带理由的 `blocked`（见 §4 D-L08-03）。
* **不引入前端框架 / 构建工具链**：`web/` 是原生 HTML + CSS + 一个 IIFE，无 npm、无打包。

* **不做证据正文渲染**（K14-2，见 §2.7）。
* **不写测试以外的新 fixture 数据**：面板喂的是实跑 `serve` 抓下来的真实响应。

## 4. Contract deviations and review registers

| ID | 事项 | 处置 |
|---|---|---|
| **D-L08-01** | 给 `PanelSection` **加** `verification_state` 字段 —— **同时是 K14 契约缺陷上报**，见 §4.1 | **加法扩展，已获 team-lead 批准（2026-09-15）**。K14-1 要求「每个 section 必须带 `verification_state`（`verified`\|`unverified`\|`blocked`）」，但 L2 给的 `PanelSection` **只有 `verified: bool`**，而 `unverified` 与 `blocked` 都是 `verified=False` —— **只有 bool 就无法在数据层区分二者**，K14-1 因此**无法机械校验**，M13-04「不得把未完成写成完成」也落不到地。这是 **K14 契约自身的内部矛盾**（要求三态，却只给 bool）。就地加法扩展 + 校验器强制 `verified ⟺ state=="verified"`，故 `verified` 字段仍在、语义不变。**建议 R-007 L2 的 K14 补上该字段。** |
| **D-L08-02** | 给 `PanelSection` **加** `facts: dict[str,str]` 字段 | **加法扩展，请 owner 审阅**。M13-04/05/07 要求面板**显示**阶段、Gate 状态、覆盖率、风险等级；L2 的 `PanelSection` 只有 `title/refs/verified/unknown_reason`，没有任何**值**通道。`refs` 必须保持纯标识符（K14-2），故另开一条**严格有界**的标量通道。 |
| **D-L08-03** | `files` 面板渲染为 `blocked` 而不是**省略** | K14 把 `files` 列为四个合法 `panel_id` 之一。静默省略一个已声明的面板，本身就是一种「藏起未完成」（A5）。渲染成 `blocked` + 具名依赖（K11）是可被机械检查的诚实。 |
| **D-L08-04** | 审批面板不渲染 `interrupt.message` —— **保守取舍，不是契约要求** | **已获 team-lead 裁决维持（2026-09-15）**。不渲染是为了严守 K14-2 的**字面**；**A5 的本意不禁止审批请求文**（`interrupt.message` 是运行时的审批请求文本，不承载「已证实/未证实」的语义判断）。信息未丢：给了 `message_ref`。这属于「多显示 vs 少显示」的**取舍**而非**正确性**问题，无明确授权时保守是对的。若 owner 要求更佳可用性，**回退一行**（把 message 放进 `facts`）。详见 §2.7。 |
| **D-L08-05** | 面板运行时不显示 `ResearchState.diagnostics` 全文 | 诊断文本会进 `blocked` section 的 `unknown_reason`（有界，最多 5 条），不作为独立 section —— 属于「不自行扩大范围」。 |

**没有静默偏离**：以上 5 条全部登记；K14 的四个 panel_id、三态取值、
`refs`/`verified`/`unknown_reason` 字段语义**未改**。

### 4.1 契约缺陷上报：K14 的 `PanelSection` 缺 `verification_state`

> **K14 的 `PanelSection` 缺 `verification_state` 字段，导致 K14-1 自身无法机械校验**
> （`unverified` 与 `blocked` 在 bool 层不可分）。本包就地加法扩展（D-L08-01），
> **建议 R-007 L2 的 K14 补上该字段**（属契约变更，须 owner 裁决）。

**缺陷论证（三步，均可机械复核）**

1. **K14 明确要求三态**。`04-l2-contracts.md` §K14 字段表写：
   `verification_state` = `Literal["verified","unverified","blocked"]`，
   并注明「**每个 section 必须标**」。
2. **K14 给 `PanelSection` 的字段集不足以承载该要求**。同节写明
   `PanelSection`：`title` / `refs`（引用 ID）/ `verified`（**bool**）/ `unknown_reason`（`str | None`）。
3. **因此两条不变量在数据层不可判别**：
   * `unverified` 与 `blocked` **都是 `verified=False`** → 无法区分
     「数据缺失」与「上游阻塞」，而这正是 M13-04 与主理人任务卡的核心要求
     （「**禁止**用无法区分的方式掩盖 `unverified` 与 `blocked` 的差别」）；
   * 「每个 section 必须标三态」在只有 bool 的类型上**不可校验** ——
     任何实现都能用一个 bool 蒙过 K14 的「可机械校验性」表格。

**本包的就地处置（不越界，可回退）**

* 在**本 lane 自己的模块**（`src/autoresearch/web_api.py`）定义 `PanelSection`，
  不碰全局串行文件 `contracts.py`（`07-lane-kickoff-convention.md` §3.2 明确要求
  「其他 lane 在自己模块里定义类型」）。
* **加法扩展**：`verification_state` 为必填；`verified` **保留**且语义不变，
  由校验器强制与三态一致。因此**既有 K14 字段契约不被破坏**，
  只是在它上面补了它自己要求却未承载的那一维。
* **回退成本**：若 owner 决定改 L2 K14（补字段），本模块的字段定义可原样保留或改为
  从共享层 import；若决定不改，本模块的自洽性不受影响（`verified` 语义未变）。

**顺带登记的第二处**：`PanelSection` **没有任何「值」通道**（只有 `refs` 标识符 +
`verified` bool + `unknown_reason` 文本），而 M13-04/05/07 要求面板**显示**阶段、
Gate 状态、证据覆盖率、风险等级。这是 D-L08-02（`facts`）的由来，属**同类缺口**
（契约声明了展示目标，但类型集没有承载它的字段）。**建议一并裁决。**

## 5. 判别力证据

### 5.1 为什么不能用「修复前基线」跑新测试

本包是**绿地**：`PanelProjection` 此前**不存在**（实测 `\bPanelProjection\b` = 0）。
新测试在 `main@8dd8780` 上**每一支都会失败**，但失败原因是
**符号缺失型**（`ImportError` / 模块不存在），**不构成判别力证据**。
如实说明，不拿它充数。

### 5.2 判据型证据 A：实跑发现的 3 个真缺陷（**发现即失败**）

`ui-skeleton-first` 第 1 步看截图时抓到 3 个实质缺陷，全部是**先有失败断言、后修**：

| # | 缺陷 | 失败形态（判据型） |
|---|---|---|
| 1 | 「阻塞」section 对**从未运行过**的项目返回 `verified("无阻塞")` | 截图 `bare-project` 显示 `verified: 1`；断言 `blockers.verification_state == "unverified"` **失败**。这正是 M13-04 明文禁止的「把未完成写成完成」，而且**只有看渲染结果才会发现** |
| 2 | 撤回 section 对**零证据**项目返回 `verified("无撤回")` | 同类；断言改为 `unverified` 后失败 |
| 3 | 审批历史把**研究想法**（`evidence_type=human` 但是 `E0`）当成审批决策 | `assert '2' == '1'`（实跑输出，见 §6） |

新增的 3 条回归测试正是为它们写的（`test_never_run_project_does_not_claim_verified_no_blockers` 等）。

### 5.3 判据型证据 B：突变测试（`web/dev/mutation_check.py`）

在**符号齐全**的前提下逐一破坏不变量，看哪支测试抓住：

| 突变 | 意图 | 结果 | 抓住它的测试 |

### 9.2 审计发现（已修）：渲染器自己派生状态，抹平了三态

**缺陷（审计提供，我已复核确认）**

```
web/styles.css:109-111   三种状态点都有定义：
                         .tab__dot--verified / --unverified / --blocked
web/app.js:244           tab.appendChild(el("span", "tab__dot tab__dot--unverified"));
                         ↑ 硬编码，--verified 与 --blocked 全树从未被应用
```

**为什么是实质缺陷**：tab 栏对**每个**面板都画「?」色点。于是
`litalpha-project.png` 里面板头显示 `BLOCKED`，**同一个 tab 却显示 unverified** ——
自相矛盾。方向虽然是**少报**而非误报正常，但它**破坏了「三态可区分」**这一 K14-1 的根基。
最讽刺的是：我自己的 `app.js` 第 7 行写着「The renderer never derives a status of its own」，
而这里它**恰恰派生了一个固定态**。

**修复**：tab 点 class 由该面板的真实 `verification_state` 派生，**且与面板头 chip 同源**
（`renderPanel` 里一次 `syncTabState(panelId, projection.verification_state)` 同时写两者，
所以二者不可能不一致）。BFF 新增 `GET /ui/panels?project_id=` 返回 `states`，
值取自**同一批 builder**（不重算）；无项目时**不返回** `states`（不猜状态）。

### 9.3 同族扫描：**确实有第二处**（主理人预判正确）

按要求扫「渲染器自己派生状态」的**全部**位置，找到第二处：

```
web/app.js:41-42   function stateOf(value) {
                     return STATE_LABEL[value] ? value : "unverified";   ← 静默强制转换
                   }
```

`stateOf()` 把**任何** K14 三态以外的取值**默认为 `unverified`** ——
同样是渲染器**凭空发明一个合法状态**。后端 pydantic 的 `Literal` 目前挡住了畸形值，
所以这条路径**当前不可达**（属开工约定 §5 的「空约束」），
但渲染器是最后一道防线，且**快照 JSON 是可手改的**。

**修复**：新增 `INVALID_STATE` 哨兵。未知取值渲染为 `INVALID-STATE` 芯片
（自己的字形 `!` / 自己的 `chip--invalid` 样式 / 原因标签写「契约违规」），
**绝不显示成三态之一**；tab 点对未知状态**不画点**（而不是画一个错颜色的点）。
`stateOf()` 由「默认值」改为「重命名」。

**扫描结论**：同族共 **2 处**，均已修。其余候选点复核为**非同类**：
`evidenceRefs()` 只是给「打回」输入框**预填一个候选 id**（非状态声明，用户可改）；
`factLookup(...) === "true"` 是**读** fact，不是派生状态。

### 9.4 新增的守卫（防止本族复发）

### 10.7 R4 修复的**边界**（team-lead 要求确认，已实测 —— 不夸大）

team-lead 要我回答：静态守卫能不能抓住「把映射表换变量名/换写法」这种改写？
**我把它拆成 6 个可执行案例实测**（`web/app.js` 上打补丁 → 跑 `-k "hardcoded or map_covers or coerce or no_browser"` + 跑 Node 守卫）：

| 案例 | 静态守卫 | Node 守卫 | 说明 |
|---|---|---|---|
| R4-a `cls \|\| "tab__dot--unverified"` 兜底 | **CAUGHT** | PASS | 静态侧按「字面量重复」抓到；**Node 侧 PASS 是正确的** —— 该兜底在 `if (!cls) return` 之后，**永不执行**，是死代码，行为等价 |
| R4-b `stateOf` 等价改写为 `: "unverified"` | **CAUGHT** | **CAUGHT** | 真回归，两侧都抓 |
| R1 真改名 `TAB_DOT_CLASS → DOT_CLASSES`（含全部引用） | PASS | PASS | **行为等价，应 PASS** —— 旧版守卫在这里会抛 `ValueError`（噪声），新版已修 |
| R2 真改名 `stateOf → renderKeyFor`（含全部引用） | PASS | PASS | 同上 |
| R3 真改名 + 映射表改写法（去空格/单行） | PASS | PASS | 同上 |
| **B2 `"tab__dot--" + "unverified"` 字符串拼接** | **MISSED** | **CAUGHT** | **静态守卫的实测盲区** |
| **B3 `"unverifie" + "d"` 拼接（stateOf）** | **MISSED** | **CAUGHT** | **静态守卫的实测盲区** |

**边界声明（如实写清，不让它看起来比实际强）**：

1. **静态守卫是「字面量形状」守卫，不是语义守卫。** 它挡住的是**字面量重复**与
   **函数体内出现真实状态名**；**字符串拼接 / 变量间接**（B2/B3 实测）**能完全绕过它**。
2. **真正约束行为的是 Node 守卫**（断言可观测 class），B2/B3 都由它抓住。
   所以本包的渲染层保证**不建立在静态守卫上** —— 静态守卫只是「便宜的早期绊线」，有已知盲区。
3. **旧版守卫还有一个我没预料到的毛病**：它锚在标识符 `TAB_DOT_CLASS` / `function stateOf(value) {` 上，
   于是**一个合法的重命名会让它抛 `ValueError`**（R1/R2/R3 在旧版下就是这种噪声失败）。
   已改为**与名字无关**：映射表按**值**定位（`\{[^{}]*"tab__dot--verified"[^{}]*\}`），
   状态函数按**行为**定位（`function \w+(value) {` 且体内读 `STATE_LABEL[value]`）。
   → 现在 R1/R2/R3 全部 PASS（行为等价就该 PASS），不再产生假失败。
4. **这条与 L-02 的 R3 是同一族问题**（AST/字面量守卫的覆盖面）：结论一致 ——
   **字面量/AST 守卫只能证明「某个写法没出现」，不能证明「语义没回归」；
   要证明后者必须有行为级断言。** 谁若只拿静态守卫当证据，就是高估了覆盖面。

### 10.7.1 权威测量表（含 team-lead 的第三条，全部实测）

team-lead 追问的第三条是「**把映射表换个变量名/换个写法**（`TAB_DOT_CLASS` → `m` 且改单行）」。
我把全部 6 个案例在同一份 `web/app.js` 上逐一打补丁、同时跑**静态守卫**与 **Node 守卫**：

| 案例 | 静态守卫 | Node 守卫 | 判定 |
|---|---|---|---|
| R4-a 兜底复制字面量 `cls \|\| "tab__dot--unverified"` | **CAUGHT** | MISSED | 静态侧按「字面量重复」抓到；Node 侧 PASS **是对的**（该兜底在 `if (!cls) return` 之后，**永不执行**） |
| R4-b `stateOf` 等价改写 `: "unverified"` | **CAUGHT** | **CAUGHT** | 真回归，两侧都抓 |
| **★ 映射表改名 `m` + 单行写法**（team-lead 的第三条） | **MISSED** | **MISSED** | **判定：PASS —— 这是正确结果**（行为等价，**不该**被标记） |
| B2 拼接绕过 `"tab__dot--" + "unverified"` | **MISSED** | **CAUGHT** | **静态盲区**（真回归未被静态抓到） |
| B3 `stateOf` 拼接绕过 `"unverifie" + "d"` | **MISSED** | **CAUGHT** | **静态盲区**（同上） |
| 控制组：真回归（`blocked` 点改指 `unverified` 类） | **CAUGHT** | **CAUGHT** | 证明这套测量**本身**是有效的，不是恒绿 |

**★ 这一行的回答（team-lead 要的）**：**「改名 + 单行」两侧都不报错 = PASS，这是对的。**
但它**必须与 B2/B3 的 MISSED 区分开** —— 同是 `MISSED`，含义完全相反：

| `MISSED` 的两种含义 | 案例 | 是否缺陷 |
|---|---|---|
| **行为等价 → 不该被标记 → MISSED 是正确判定** | ★ 改名 + 单行 | **不是缺陷**（这正是假失败修复生效的证据） |
| **真回归 → 该被标记却没标记 → MISSED 是盲区** | B2 / B3 | **是盲区**（已写明，由 Node 守卫兜住） |

**旧版守卫在 ★ 这一行的表现（本轮修正掉的缺陷类）**：旧实现锚在标识符上
（`source.index("var TAB_DOT_CLASS = {")` / `source.index("function stateOf(value) {")`），
于是 ★ **抛 `ValueError` → 守卫红**。**行为没回归而守卫红 = 假失败**。
这是**独立于「假通过」的第二个缺陷类**，见 §10.8 的回归测试。

**为什么留着静态守卫**：它零成本、失败信息直指代码位置，且能抓住「有人又抄了一份字面量」这类
真实退化；但**它的绿不构成语义保证**，这一句必须和它一起读。

### 10.8 假失败（false failure）：第二个缺陷类，已有回归测试守住

**缺陷类定义**：**行为没有回归，但守卫报红。** 与「假通过」（缺陷存在而守卫绿）方向相反，
但危害相同：它使守卫**不可信** —— 要么阻塞合法重构，要么诱导后来者去**放宽守卫**（把真正的保护也一起削弱）。

**本轮实例**：我为 R4 写的第一个强化版把守卫**锚在标识符**上
（`TAB_DOT_CLASS` / `function stateOf(value) {`）。一个**合法重命名**就会让它抛 `ValueError`。

**修法（守卫应锚在语义上，不是锚在名字上）**：
- 映射表**按值定位**：`\{[^{}]*"tab__dot--verified"[^{}]*\}` —— 不关心它叫什么、在哪一行；
- 状态函数**按行为定位**：`function \w+(value) {` 且体内读 `STATE_LABEL[value]` —— 不关心函数名。

**新增两条测试**（本类缺陷的守护者）：

| 测试 | 断言 |
|---|---|
| `test_guards_are_name_independent_and_do_not_false_fail` | 对 4 种**行为等价的改名/改写法**（改名映射表 / 改名状态函数 / 两者都改 / 两者都改 + 映射表单行化），三个守卫 helper **不得抛异常**，且**判定与原始源一致** |
| `test_renamed_renderer_is_behaviourally_equivalent` | **证明**上面那些改名确实是行为等价的 —— 用 `render_contract_check.mjs --app=<改名后源码>` **真跑**渲染器；并含**负控制组**（同一 harness 喂一个真回归必须失败），否则「returncode == 0」什么也证明不了 |

**反事实验证（本测试确实有判别力）**：把 `_dot_class_map_keys` **改回**标识符锚定版
（`source.split("var TAB_DOT_CLASS = {", 1)[1]…`）后，
`test_guards_are_name_independent_and_do_not_false_fail` **FAILED**（断言失败，非收集错误 ——
突变后已 `ast.parse` 校验过语法，避免把「语法错误导致的红」误当判别力）。

**顺带的一处工具改动**：`render_contract_check.mjs` 新增 `--app=<path>`（默认 `web/app.js`），
使它能对**变体源码**跑同一组检查 —— 这是上面「证明改名行为等价」得以成立的前提。
这也意味着**该脚本的 hash 变了**，需重新冻结。

**与 team-lead 记的 §3.8 的关系**：他把「修复对 ≠ 守卫对」与本条合并为
「**守卫红过/绿过都单独不构成证据**」。本节的贡献是给出**该判据的可执行形式**：
守卫必须同时被证明「**该红时红**」（负控制组）与「**不该红时不红**」（行为等价改名 → PASS）。
