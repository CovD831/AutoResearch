## 1. 缺陷（实测复现）

同一篇论文（`doi=10.1/same`）连续检索 3 次：

```
paper_ids: ['paper_3e04954fa65f43c3', 'paper_4bc0192016254c56', 'paper_5f...']
wiki pages: 3      evidence: 3
```

**根因（已定位到行）**：`_to_record` 构造 `PaperRecord` 时不传 `paper_id` → 走
`contracts.py` 的 `new_id("paper")`（**随机**）→ 每次检索新 id → 新 `page_id` → 新 wiki 页 + evidence。
`_dedupe_key` 已算出稳定标识，但只喂**单次调用内**的 `seen` 集合，跨调用失效。

## 2. Implemented design

### 2.1 确定性标识 `bibliographic_paper_id`（`search_service.py`，新增）

```python
def bibliographic_paper_id(paper: PaperRecord) -> str:
    if paper.doi:
        key = "doi:" + paper.doi.lower().strip()
    else:
        key = "title:" + re.sub(r"\W+", "", paper.title.lower())
    digest = hashlib.sha256(f"{paper.project_id}\x1f{key}".encode()).hexdigest()[:16]
    return f"paper_{digest}"
```

- **哈希而非直嵌**：标题键可能极长且不是合法 id 片段；`sha256[:16]` 保持 `paper_<16 hex>` 形状。
  **确定性哈希，不引入新随机源。**
- **`project_id` 进摘要（D3，偏离规格文字）**：store 主键 `(kind, record_id)`（`storage.py:94`）
  **不含 project**，`KnowledgeService.get_page` 也走该全局键。若只用 `doi:...`，项目 B 检索同一
  DOI 会解析到项目 A 的页并**跳过 B 自己的写入** → 跨项目污染（CF-G 判据型实测）。

### 2.2 标识在**唯一choke point**派生（第二轮 ①②③）

`_identity_normalized(paper)`：**仅当记录没有显式 `paper_id` 时**才派生。

- 用 `model_fields_set` 区分「调用方给了 id」与「id 来自 `new_id` 默认值」（已实测四种构造路径）。
- **显式 id 被尊重**：用户 seed 自带 id、provider 回显自己 id 时保留（③）。
- **派生点只在 `persist_bibliographic_record`**：`_to_record` **不再**派生（第二轮改动），
  因为它只覆盖 adapter 命中；legacy connector 命中与 seed 走不到那里。三条入口共用同一实现
  —— 与 A1「parity 由结构保证，而非两个编辑者记得同步」同一原则。
- 结果：① adapter 命中、② legacy 命中、③ 重建的 seed 都收敛到同一 id。

### 2.3 幂等写入 + 单一临界区（`persist_bibliographic_record`，改写）

```python
paper = _identity_normalized(paper)
with store.transaction():                      # ← ① 检查与写入同一临界区
    existing_item = _persisted_bibliographic_evidence(evidence, paper)   # valid_only=True（⑤）
    existing_page = knowledge.get_page(paper.paper_id)
    if existing_item is not None and existing_page is not None:
        return <stored paper>, existing_item   # D1：完全落库 → 零写入
    store.put(...)                             # upsert
    if item is None: item = evidence.add(...)  # evidence 缺失/失效才重铸
    if existing_page is None:
        knowledge.add_page(WikiPage(revision=1, ...))
    elif item.evidence_id not in existing_page.evidence_ids:
        knowledge.add_page(WikiPage(revision=existing_page.revision+1,  # ④ 回填
                                    supersedes=existing_page.revision_id, ...))
```

- **① 竞态**：原先「读存在性」与「写三份记录」是分离语句。两线程交错时都看到「不存在」→ 双写
  evidence，或一方 `add_page` 撞 `revision=1` 抛 `ValueError`。`store.transaction()` 全程持有
  store 的 `RLock`，嵌套的 `put` / `add_page` 以可重入方式取同一把锁。
  **可接受性论证**：该锁本就是本 store 实例所有写入的既有串行点；临界区只含 2 次读 + ≤3 次写；
  运行期检索本身近似串行。**代价**是同一 store 实例内的并发写被粗粒度串行化；
  **残留**：跨进程（多进程共享同一 db 文件）不受此锁保护，见 §8。
- **④ 回填**：页在、evidence 不在时，新铸的 evidence 必须被页引用，否则成为孤儿、页→证据链断裂。
  `add_page` 是 append-only，故**只能以新 revision 回填**（`revision+1`、`supersedes`），不能改旧版本。
- **⑤ 失效证据**：`_persisted_bibliographic_evidence` 必须 `valid_only=True`。否则被 invalidate 的
  E1 会被当成「已落库」→ (a) 永久抑制重铸，(b) 把**失效**条目当当前记录返回。
- **D1 零写入**：完全落库时提前返回。**这不是可删的冗余**，见 §5 D5。

## 5. Decisions

- **D1 幂等跳过**（owner）：检索路径只落库，无元数据更新需求；不写新 revision。
- **D2 不统一 `author` / `actor`**（owner）：`author`=模块名，`actor`=调用方；加测试钉住。
- **D3 标识含 `project_id`**（我提出，偏离规格文字，待背书）：理由见 §2.1，CF-G 判据型已证。
- **D4 半写自愈 + 新 revision 回填**（审计④）：只补缺失的一半，页侧以 `revision+1` 回填引用。
- **D5 保留「完全落库 → 提前返回」（**与审计⑥ 的「删掉冗余早退」相反**，需裁定）**：
  实测证据 —— 删掉该早退后，**同一内容的重检索会改写已落库记录的 `retrieved_at`**
  （`{WITH: False, WITHOUT: True}`，见 §7 探针）。这使重检索不再是零写入，与 **D1「已存在则不再写入」
  逐字冲突**，并让 durable 记录随检索次数漂移。缺陷 ⑥ 指出的「重复检查」已通过收敛为
  **单一存在性判定 + 早退 / 自愈两条出路**解决；早退保留为 D1 的语义承载，而非冗余。
  **若 owner 仍要求删除，请连同 D1 的措辞一并修改。**
- **D6 显式 id 优先于派生**（审计③）：用户 seed / provider 自带 id 时保留；仅无显式 id 时派生。

## 6. Invariants

- 同一 `(project, 书目键)` → 同一 `paper_id`，跨调用稳定，不引入新随机源。
- 同一 `(project, 书目键)` 的 paper / **有效** evidence / wiki 页各至多 1 份。
- **存在性检查与写入在同一临界区内**（否则双写或崩溃）。
- 失效 evidence 不算「已落库」；页存在但有效 evidence 缺失时必须回填引用。
- 页的 `evidence_ids` 不得引用不存在的 evidence id（自愈后）。
- 不同 project 的同一书目键互不影响。
- 两条检索路径 + seed 共用同一标识派生实现（结构性一致，非人工同步）。
- `_persist(self, paper)` 签名不变（A2 崩溃注入依赖）。
- 不改 `contracts.py` / `storage.py` / `evidence.py` / `knowledge.py`。

## 8. Known limitations

- **⑦ 标题分支的同键碰撞现在是持久的**：`re.sub(r"\W+","",title)` 下 `"A B"` 与 `"AB"` 同键。
  该归一化本就存在（此前只影响单次运行的 `seen` 集），但**现在会永久共用一页 / 一条 evidence**
  —— 只是「少建了一页」，不会污染别的记录的内容（页正文取首写者）。带 DOI 的记录不走此分支。
- **跨进程竞态未闭合**：`store.transaction()` 的 `RLock` 是**进程内、实例级**的。多进程共享同一
  db 文件时不互斥。当前运行时是单进程（`application.py`），故未处理；若将来多进程写作，需在
  SQLite 层做原子插入（`INSERT ... ON CONFLICT` 语义）而非 check-then-act。
- **provider 自带 `paper_id` 时不被派生**：当前三个 connector 均不返回 `paper_id`（a2 测试 fixture
  会，故其保持既有 id）。若将来某 provider 回显 id，同一论文跨 provider 可能不收敛。属 D6 的已知代价。
- **evidence 存在性查询 O(n)**：`EvidenceService` 无 `by_source_id` 入口，`list(project_id)`
  全量扫描；一轮 N 篇 → O(N²) 次 `get`。
- **① 的测试是概率性判据型**（见 §4 诚实边界）。
- **未做跨进程并发验证**（沿用 A5/A8 挂账口径）。
- 未生成 `task-package.json`（规格交付物未列）。
