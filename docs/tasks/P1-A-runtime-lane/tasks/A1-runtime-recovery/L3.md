## 具体输入输出类型

- `PaperSearchRequest`：`project_id`、`run_id`、`invocation_id`、bounded `query`/`limit` 和 seed papers。
- `PaperSearchInvocation`：请求、`PaperRecord[]`、诊断、`EvidenceCandidate[]` 和 `InvocationReceipt`。
- `InvocationReceipt.status` 表示本次读取视图；`outcome_status` 保留真实业务终态，使 replay 不丢失原始结果。
- `CapabilityManifest` 仅保留 S1 所需的 name/kind/version/permissions；trust tier 不由 adapter 自行提升。

## 状态迁移

```text
absent --reserve--> pending(reserved)
pending(reserved) --service start--> pending(service_started)
pending(service_started) --service result staged--> pending(service_returned)
pending(service_returned) --finalize--> finalized(outcome_status)
pending --explicit recover/fail--> finalized(failed|unknown_outcome)
finalized --exact request--> replayed(view of original outcome)
finalized --conflicting fingerprint--> rejected
```

合法终态为 `completed`、`completed_empty`、`failed`、`unknown_outcome`；`replayed` 只用于返回视图，不覆盖原始 outcome。

## 持久化和事务边界

- 复用现有 `RecordStore.idempotency` 表，不新增 Store、数据库或消息总线。
- `reserve_idempotent` 在同一 SQLite 事务内写入 pending 和 request fingerprint；成功后才允许调用 service。
- pending 内部阶段按 `reserved -> service_started -> service_returned` 单向推进；阶段事件用于区分尚未发出、已发出未返回和已收到结果未最终登记。
- `service_returned` 同时暂存规范化 invocation result；若进程在最终登记前重启，恢复可以直接 finalize 暂存结果，不再次调用 connector。
- `finalize_idempotent` 只允许把 pending 收口为 finalized，保留原始 request、fingerprint 和时间戳。
- `get_idempotent`/`list_idempotent` 只读 durable record，支持新进程重启后的 replay 和 parity。
- audit event 记录 reserve、finalize、recover 三个可观察节点；不写 EvidenceItem 或 GateDecision。

## 外部副作用和幂等策略

- 幂等 scope 使用 manifest name，key 使用 `run_id:invocation_id`。
- fingerprint 对 bounded request 的 JSON 规范化后 SHA-256；同 key 不同 fingerprint 明确拒绝。
- 精确 replay 读取已保存的完整 invocation，connector/service 不再调用。
- adapter 只产出 EvidenceCandidate；当前 legacy service 的内部 `_persist` 双表示问题留给 B-1/主线集成裁决。

## timeout / pending / unknown / restart 恢复

- `TimeoutError` 统一收口为 `unknown_outcome`，因为 provider 是否产生了副作用不可确定。
- service 返回空结果且无不确定诊断时为 `completed_empty`；网络禁用、provider failure/unavailable 等诊断为 `unknown_outcome`。
- 进程在 reserve 后崩溃会留下 pending；再次调用默认抛出 `PendingInvocationError`，不得自动成功或隐式重试。
- `recover_pending`/`fail_pending` 是显式操作，只能收口为 `failed` 或 `unknown_outcome`，并追加审计事件。
- 新 `RecordStore` 实例读取同一 SQLite 文件即可 replay，不重复 connector 或 durable facts。

## 实现与教学循环（用户验收门禁）

这部分是本任务的工作方式，不改变代码架构或 R004/R005 冻结决策：

1. **先看现状**：指出当前代码、任务包和约束，说明这一小步要解决的运行时风险。
2. **补前置知识**：用本轮需要的概念解释设计，例如幂等、receipt、状态机、reserve-first、replay、recovery、parity 和 fail-closed；同时说明不用更大抽象的理由。
3. **做最小实现**：只改当前切片允许的路径，并说明输入、输出、持久化边界和失败语义。
4. **展示自动证据**：运行专项测试、静态检查和可重跑报告，明确哪些是本地自动化证据，哪些不是用户验收。
5. **用户亲自验证**：由用户运行或复核验收场景，至少确认重复提交、冲突 fingerprint、空结果/未知结果、pending 恢复和 parity 报告；用户未确认前保持 `handoff`，不得标记 `accepted/done`、推送或合并。
6. **记录与复盘**：把用户反馈、最终决策、命令结果和下一步写入 task-local ledger；自动化证据不能替代用户确认。

P1-A 的教学切片顺序为：

- 合同与 fingerprint：为什么请求身份和业务结果必须分开；
- reserve/finalize：为什么副作用前必须先留下 pending；
- replay：为什么重放只能返回已保存结果，不能再次调用 connector；
- timeout/recovery：为什么未知结果必须 fail-closed，恢复默认显式收口；
- parity：为什么比较 durable facts 和语义投影，而不是随机 ID 或“都运行过”。
