# S4-A2 Experience Wiring L3

## Task source

`docs/tasks/P1-A-runtime-lane/TASK-SPECS.md` 的 A6 节（「失败经验自动沉淀」「A6 = 经验沉淀接线」）要求把 A3/B3 产生的 fail-closed 拦截事件接到 `ExperienceService`，让失败经验自动沉淀并为 promote 的「复现 ≥2」门槛提供真实基数；registry 行 `S4-A2-EXPERIENCE-WIRING`（`docs/rearchitecture/TASK-PACKAGE-REGISTRY.md`，`ready`），前序依赖 `S3-A2-PROVIDER-LANE`（O12）与 A3/B3 accepted。

基线：`origin/main@1e7e196`（2026-09-12 已 rebase）。本包真实改动以 `--base origin/main` 为准。

## Implemented design

1. **消费口 = 只读拉取，不是订阅**（D-A6-01）。`ExperienceSink.settle(project_id)` 经 `RecordStore.events(project_id)` 读已落地的事件日志，对 `audit_events` 表零写入。产生侧（`audit_evidence.py` / `audit.py`）均在 `forbidden_paths`，push 式钩子结构上无法落地。
2. **映射表** `MAPPING_RULES: dict[event_type, parser]` —— 交付物本体在代码里，不在文档里：

   | 事件类型 | 触发判据 | technique | problem | outcome | evidence_ids |
   |---|---|---|---|---|---|
   | `evidence.candidate_blocked` | 事件存在即成立（payload 即 `EvidenceAdmissionResult`） | `evidence_admission_blocked` | `"; ".join(reasons)`，无 reasons 时用稳定兜底串 | `evidence candidate <id> blocked at admission (n reason(s))` | `[]`（blocked 意味着没有准入的证据） |
   | `audit_evidence.report_created` | `status == "fail"` | `audit_evidence_remediation` | 第一条 `unverified_claims`；否则第一条 verdict `reasons`；否则稳定兜底串 | `audit evidence report <id> status=fail (n unverified claim(s))` | `admission_results[].evidence_id` ∪ 各 verdict 的 `evidence_ids` |
   | `audit_evidence.report_created` | `status == "unknown"` | `audit_unknown_resolution` | 同上 | 同上（`status=unknown`） | 同上 |
   | `audit.report_created` | `unknown_count > 0` | `audit_unknown_resolution` | `audit runtime produced n unknown verdict(s) that need evidence` | `audit report <id> finished with n unknown verdict(s) of m` | `[]`（payload 无证据字段） |

   未被判据命中的事件（`status=pass`、`unknown_count=0`）**被消费但不产出记录**，保证 settle 结果可复现。
3. **同因去重键** = `f"{technique}|{normalize(problem)}"`（`_recurrence_key`）。只含冻结字段，**不含 event_id、不含计数**，所以两次同因拦截会命中同一条 record 与同一个 `experience_id`。
4. **`experience_id` 确定性派生**：`"exp_" + sha256(f"{project_id}|{recurrence_key}")[:16]`，长度与 `new_id("exp")` 一致。好处：重跑写的是同一条记录而不是新记录，且无需额外索引表。
5. **消费标记**（D-A6-02）：`RecordStore.remember_idempotent(SINK_SCOPE="experience_sink", key=event_id, result={...})`。`INSERT OR IGNORE` 的 `rowcount` 即「本次是否首次消费」。不新建表、不改 `storage.py`。
6. **`recurrence_count` 是派生的**：`1 + (同项目同 `recurrence_key` 的 `mapped=True` 标记数)`。顺序是「先写记录、后写标记」，于是「记录写成功、标记未写」的崩溃是自愈的：重跑得到同样的计数并重写同样的记录。标记表不可读时降级为 1（下次健康 settle 自动纠正）。
7. **四门槛以下**（D-A6-03）：新建记录恒 `grade=E0 / promoted=False`；合并已存在记录时只允许把 `recurrence_count` 取 max、并把 `evidence_ids` 取并集，`grade` 与 `promoted` 原样保留。AST 级证明：`experience_sink.py` 的调用点集合里没有 `promote`（也没有 `append_event`、`add_page`）。
8. **写入通路唯一**：只调 `ExperienceService.record` → 它只写 `KnowledgePartition.EXPERIENCES` 的 record 与 WikiPage 镜像。实测一次 settle 新增的 `audit_events` 行类型集合恒为 `{"knowledge.page_added"}`。
9. **降级方向 fail-closed**：`settle` 永不抛。五类降级各有诊断：事件日志不可读、消费标记不可读、单条 payload 不可读（`MalformedEventPayload`）、`experiences.record` 写入被拒、消费标记写入被拒。后两类**不标记已消费**，事件留给下次重试。
10. **payload 读取防御化**：`_string_list` 让「字段类型被改成裸字符串/dict/None」退化为空列表而不是按字符迭代；`unknown_count` 非数字退化为 0（即不判为失败）。裸字符串 `reasons` 实测产出兜底 problem，不是崩溃也不是逐字符垃圾。

## Deliberate non-goals

- 不做真正的发布/订阅总线（R005 禁止新增消息总线 / scheduler / 隐藏 Agent）。
- 不改 `ExperienceService.promote` 的四门槛，不给自动晋级留路径。
- 不写 experiences 以外的分区；不直接调 `KnowledgeService.add_page`。
- 不触碰 B 线 evidence 路径与 A3 audit 运行时（`forbidden_paths`）。
- 不做事件级 replay / 游标 / 回溯窗口（复用既有 `idempotency` 底座已足够）。

### D-A6-05 详述：`failure` 标签的落点与验证

规格要求的是「`ExperienceRecord` 打上 `failure` 标签」。当前落地结果：

| 落点 | 谁能改 | 结论 |
|---|---|---|
| `ExperienceRecord` 字段集（`contracts.py:367-376`） | 共享 schema | 已增加 `tags: list[str] = Field(default_factory=list)` |

## Known limits

- **只读保证是「本模块不调 `append_event`」+「产生侧不在本包」的结构保证**，不是数据库层权限：`ExperienceSink` 持有 `RecordStore`，若有人在本模块里新增一次 `append_event` 调用即会破坏该保证。守护它的是 `test_sink_module_has_no_call_site_that_appends_events_or_promotes`（AST 级），而不是类型系统。
- **「同因」的定义是我方判据，不是产生侧声明**：判据是 `technique|normalize(problem)`。若产生侧改了 reasons 的措辞（多一个标点、换词），同一次故障会被算成两个 cause、两条记录、各自 `recurrence_count=1`。这是「复现 ≥2」门槛的一个真实脆弱点，owner 若要在生产上依赖该基数，应把 cause 判据改成产生侧显式给出的稳定原因码。
- **`_match` 的「映射表外的 event_type」分支在公开 API 上不可达**（两个调用方都先按 `MAPPING_RULES` 过滤），它只是内部防御；靠直接单测覆盖。
- **不是审计链条的一部分**：settle 产生的经验记录不参与任何 gate 判定，也不回写 audit 报告。
- 事件日志是全项目维度的（`events(project_id)` 不带类型过滤），每次 settle 会扫全量再筛；10⁵ 量级事件下需要分页或加时间下界，本包未做。
