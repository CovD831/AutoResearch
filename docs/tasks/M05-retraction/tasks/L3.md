## 2. Implemented design

### 2.1 K10-3：复用 B5，不重写

**判据读取点实测行号**：`external_sources.py:254-255`（`updated_by = message.get("updated-by") or []`
/ `update_to = message.get("update-to") or []`），位于 `CrossrefAdapter._from_live`（`:234`）。
B5 的 fail-closed 修复仍在原位：`resolver_record`（`:352`）对 `UNKNOWN`/`NOT_FOUND` 返回 `None`。

`retraction.py` **不读关系数组**。它消费 `CrossrefAdapter.resolve()` 的 `DoiVerdict`，
把 `SourceStatus` 投影成 K10 的四个值。有一个 AST 级守卫测试
（`test_retraction_module_does_not_re_read_the_relation_arrays`）断言 `retraction.py` 的
**非 docstring 字符串字面量**里不出现 `updated-by` / `update-to` / `license`——即「重新实现判据」
这件事在结构上被禁止，而不是靠约定。

### 2.2 K10-1：`UNAVAILABLE` 不是 `ACTIVE`（本包核心）

投影表（`retraction.py:60-66`，**数据而非分支**，可脱离传输校验）：

| B5 `SourceStatus` | K10 `RetractionStatus` | 理由 |
|---|---|---|
| `FOUND` | `ACTIVE` | 唯一允许产生 `ACTIVE` 的输入 |
| `RETRACTED` | `RETRACTED` | |
| `CORRECTED` | `CORRECTED` | |
| `NOT_FOUND` | `UNAVAILABLE` | DOI 解析不到不是「确认没问题」 |
| `UNKNOWN` | `UNAVAILABLE` | 传输失败/限流/超时 |

三条落地保障：

1. **表是全覆盖的**，且有一个测试断言「`ACTIVE` 的原像恰好等于 `{FOUND}`」
   （`test_only_an_explicit_found_projects_to_active`）——未来新增 `SourceStatus` 成员会让该断言失败。
2. **未映射的成员抛 `UnmappedSourceStatusError`**，不返回默认值
   （`retraction.py:100-113`）。
3. **resolver 抛异常也走同一个投影**（`retraction.py:226-242`），
   避免「异常路径」与「表路径」两个决策点各说各话；异常类型记入 `reasons`。

「取不到」与「确认未撤稿」两个结论**没有被坍缩**：`RetractionCheck.source_status` 保留 B5 原始状态，
`reasons` 保留 B5 的理由串，所以 `NOT_FOUND`（不存在）与 `UNKNOWN`（取不到）在 K10 之外仍可区分。
外部负例只断言 `status is UNAVAILABLE` 且 `confirmed_active is False`。

**投影层允许归并，审计层禁止归并**（owner D-M05-01 裁决的附加条件）：`not_found` 与 `unknown` 都投影为
`UNAVAILABLE`（K10 是冻结的 4 值枚举，粗是刻意的），但 `source_status` 与 `reasons` 必须保持可区分，
否则审计者再也分不清「这个 DOI 不存在」与「我们够不到 Crossref」。该性质由
`test_not_found_and_unknown_merge_at_the_projection_layer_only` 固化——**抹掉 `source_status` 的变异
会让它失败**（§5.3 探针 4），这是「将来有人『优化』掉 `source_status` 时有人拦得住」的机制。

**`ACTIVE` 不蕴含「今日可达」**：快照兜底可以在 live 失败时给出 `ACTIVE`，此时 `transport_degraded` 为真。
这条已写进 `retraction.py` 的模块 docstring 并配测试（`test_active_with_a_degraded_transport_is_flagged`）；
需要新鲜确认的调用方只看 `ACTIVE` 是不够的。

### 2.3 K10-2：`RETRACTED` 必须真的传播（含 D1/D2 接缝修复）

K8 的 `invalidation.py` 归属于 L-02。本 base 上**不存在**（实测 `ls` / `git show main:` 均失败），
按开工约定 §3.3「跨 lane 契约只引用，不重定义」，本包**不定义 K8 类型**，只声明一个端口：

```python
@runtime_checkable
class InvalidationSink(Protocol):
    def propagate(self, *, source_evidence_id, reason, affected_claims,
                  affected_gates, action) -> object: ...
```

**「不是只标记状态」是靠结构保证的**：

- `RetractionChecker.check(doi, *, context)` 在 `RETRACTED` 时**必须**调用 sink；
- **没接 sink → 抛 `PropagationRequiredError`**，而不是返回一个「看起来已传播」的状态；
- `source_evidence_id` 为空 → 抛错；
- `action` 由 `k8_action_for(reason)` 决定，`permanent_block` 三类（`forged`/`paywall_bypass`/
  `unapproved_egress`）**不可降级**（K8 不变量 1），未映射的 reason 抛 `UnmappedPropagationReasonError`。

#### 2.3.1 D1：两侧对「谁推导 claims」的分歧（**已修，改在 L-04 侧**）

L-02 落地后的真实签名实测为 `propagate(*, source_evidence_id, reason, actor="system")`
（`invalidation.py:254-260`），且**自己从图里推导** blast radius
（`:268-274`：`claims_for_evidence` → `gates_for_claims`）。

**判决：L-02 的设计是对的，修 L-04 侧。** K8-2 要求「传播到关联 claim 与 Gate」，而**只有图知道那个
关联关系**。让调用方传 claims，等于让一个看不见图的模块替图做判断——K8-2 就成了调用方的责任而不是
K8 owner 的责任；而且 L-04 传进来的 claims **根本无从校验**。

**本包原来的写法是错的**（这是 D1 在我这边的根因）：`PropagationContext.affected_claims` 是**必填**，
且空集抛错「镜像 K8-3」。它强迫调用方编造它不可能知道的图事实，并把 K8-3 的守卫**从 owner 手里搬走**。
现在：

| 项 | 原来 | 现在 |
|---|---|---|
| `PropagationContext.affected_claims` / `affected_gates` | **必填** | **可选**（默认 `()`）；空 = 「本模块不作断言，由 K8 从图推导」 |
| 空 `affected_claims` | L-04 抛 `PropagationRequiredError` | **不抛**——交给 K8，由 L-02 的 `BrokenPropagationError`（K8-3）在能真正行走图的那一侧拒绝 |
| `source_evidence_id` 为空 | 抛错 | 抛错（保留） |

#### 2.3.2 适配器 `K8InvalidationAdapter`（`retraction.py` 内）

适配 L-04 的 5 参调用 → L-02 的**两步 API**：`plan()`（纯推导、零副作用）→ 交叉校验 → `record(plan)`（落库 + 审计）。
**它不「丢掉多余参数」，而是把它们当断言做交叉校验**：

| 校验 | 时机 | 不一致时 |
|---|---|---|
| `action` == `action_for_reason(reason)` | 构造 plan 之前 | 抛 `PropagationContractMismatchError`（D2：两张 K8-1 表必有一张过期） |
| 断言了 `affected_claims` → 必须等于 plan 推导出的集合 | **落库之前** | 抛 `PropagationContractMismatchError` |
| 断言了 `affected_gates` → 同上 | **落库之前** | 同上 |

**「拒绝 ⇒ 什么都没落」是结构性的，不是时序性的。** 因为 `record(plan)` 落库的**就是被校验的那个对象**，
校验与被落库之间**没有窗口**——竞态在构造上不可能存在，所以不需要任何写后回补校验。

> **这个「结构性」有一个本包无法自证的前提**（L-02 复核时提出，已采纳）：`plan()` 必须**无副作用**。
> 本包从调用方只能核对**可观测部分**（返回对象的 blast radius），形状不符会**响亮失败**
> （读 `plan.affected_claims` 直接 `AttributeError`），不会静默；但「`plan()` 里没有偷偷写库」这一属性
> 属于 **K8 owner 的契约与测试**，不在本包能证明的范围内。
> → 因此本包只说「**在 `plan()` 无副作用这一前提下**，拒绝 ⇒ 什么都没落是结构性成立的」，
> 不说「本适配器证明了这一点」。**这是 L-02 提醒的正确修正**：`hasattr(service, "plan")` 只证明**形状**，
> 证明不了**语义**。

> **这是 D-M05-09 的根本修法，而不是绕过。** 演进过程值得记下：
> ① 最初在 `service.propagate()` **返回之后**校验 → 合并树实跑抓到「错误报了、事实已落库」（§5.5）；
> ② 改为在写之前读 `service.graph.claims_for_evidence` 直接取推导结果 → 时序修好了，但**伸手进了 K8 的内部属性**；
> ③ L-02 拆出 `plan()`/`record()` 后改为现在的写法 → **既零内部伸手、又零重复遍历、且校验时机由构造保证**。
> 第 ② 步的写后回补校验因此**已删除**（它防的那个竞态现在不可能发生）。

**不复用 `propagate()`**：它等价于 `record(plan(...))`，但调用方拿不到 plan，也就在落库前没有可校验的对象。
适配器因此要求所接 service 暴露 `plan()`；没有就抛 `K8UnavailableError`（**拒绝**，不退化到「事后校验」）。
正常路径（调用方不断言）同样走 plan，所以只有一条代码路径。

**K8 模块的 import 是惰性的**（`K8_MODULE` + `_k8_module()`）：`invalidation.py` 是 L-02 的排他文件、
不在本 lane 的 base 上，模块级 import 会让 `retraction.py` 在那个 base 上彻底不可导入。
惰性只把失败挪到使用点，并给它一个名字（`K8UnavailableError`）。

**端口的判别成员与接线期守卫（D-M05-13，falsify-r007 独立复核发现）。** 裸 `InvalidationService` 有一个
叫 `propagate` 的方法，而 `runtime_checkable` 的 `isinstance` **只查成员名、不查签名**——于是它会
**通过 `isinstance`**，然后在首次调用时抛裸 `TypeError`。绿灯挂在坑上，这是本包端口设计的一个真缺陷
（不是理论问题：独立复核直接复现了）。修法两层：

1. 协议声明一个**非方法成员** `implements_retraction_sink: bool`。`runtime_checkable` 会检查非方法
   成员是否存在，所以裸 service 的 `isinstance` 从 `True` 变成 **`False`**——**绿灯不再说谎**。
   `K8InvalidationAdapter` 与两个测试替身显式声明它。
2. `RetractionChecker.__init__` 对不合形 sink 抛 `PropagationRequiredError`，**消息带修法**：
   `wrap it: sink=K8InvalidationAdapter(service)`。**接线错误在接线那一行报**，而不是在首次传播中段
   以一个指向 service 的 `TypeError` 报。

### 2.4 M05-06 的 OA/许可事实层（怎么判定，不管策略）

**分工**：本包只回答「记录声称的访问基础是什么」；**谁能看/导出/删除**是 K11 / L-09 的
`licensing.py`。`RetrievalDecision` 的 docstring 明确写了这一点。

许可判定落在 `external_sources.py`（Crossref payload 解释本来就是该模块的职责），新增：

- `AccessStatus`（`OPEN`/`RESTRICTED`/`UNAVAILABLE`，`:74`）—— 原表「OA/授权/不可用三态可区分」；
- `LicenceVerdict`（`:121`）—— 事实投影，含 `licence_urls` / `content_versions` / `transport` / `reasons`；
- `CrossrefAdapter.licence(doi, message=None)`（`:395`）；
- `CrossrefAdapter.verdict_from_message(doi, message)`（`:382`）—— 让录制 payload 能走**同一条**
  `_from_live` 判据，离线分类且不必重实现方向。

**判定规则（每一条都由实测真实 payload 支撑，见 §5.1 的 5 个真实 DOI）**：

1. 只有**显式开放许可 URL**（`creativecommons.org/licenses/`、`creativecommons.org/publicdomain/`）
   才算 `OPEN`。无法识别的许可 URL **一律不算开放**——「不认识」不是「开放」。
2. `content-version == "tdm"` 的条目**永不作阅读基础**（`_TDM_CONTENT_VERSION`，`:470`）。
   理由与实测：Elsevier（`https://www.elsevier.com/tdm/userlicense/1.0/`）与 Springer
   （`http://www.springer.com/tdm`）都以 `tdm` 到达且都是订阅作品；唯一开放的
   PLOS ONE（CC-BY）以 `unspecified` 到达。
   → **「有 `license[]` 条目」≠「开放获取」**，这是本层的真实陷阱（见 §5.3 探针 3）。
3. **没有 `license[]` 元数据 → `UNAVAILABLE`**（不是 `OPEN`）：缺失不是许可。
4. 传输失败 / 403 / 404 / 未接 client → `UNAVAILABLE`。
5. `delay-in-days > 0`（禁运期）记入 `reasons` 但不改变状态（不静默消失）。

### 2.5 N-3：拒绝绕过付费墙

`RetractionChecker.decide_retrieval(doi, *, bypass_paywall=False, context=None)`：

- `bypass_paywall=True` → **抛 `PaywallBypassRefused`**，**对所有作品**（含开放作品）都一样——
  被拒绝的是**「绕过」这个模式本身**，不是某个许可状态；
- 调用方给了 `context` 时，先按 K8 记一条 `paywall_bypass` + `permanent_block` 再拒（K8 不变量 1）；
- 未请求绕过时：只有 `OPEN` 才 `granted=True`，`RESTRICTED`/`UNAVAILABLE` 都不授权，
  `basis` 分别是 `restricted`/`unavailable`。

### 5.6 折叠语义实测（**供老板裁决用**，`invalidation.py` = `391644fe…`）

L-02 给 `plan()` 加了**可选** `propagation_id`（调用方定义「什么算同一次失效」），并声称两条折叠语义。
本包**不靠读代码确认，直接实测三个场景**（脚本 `/tmp/m05_fold_probe.py`）：

| 场景 | 实测输出 |
|---|---|
| **A) 同一事实重试 + 稳定 id** | `p1.created_at ≠ p2.created_at`，但 `record(p2)` **折叠**：`returned same propagation_id: True`、`returned ORIGINAL created_at: True`、`records/events = (1, 1)`。<br>→ L-02 的说法 **成立**；且证明他的 `VOLATILE_FIELDS={"created_at"}` 修复**是必需的**——没有它，两次 `created_at` 不同会被判成「同 id 不同内容」而**拒绝一次合法重试**。 |
| **B) blast radius 变宽 + 同一个稳定 id** | `claims: ['claim_alpha'] → ['claim_alpha','claim_beta']`，`record(p2)` **抛 `InvalidationContractError`**（"already stored with different content"），`records/events` 停在 `(1, 1)`——**拒绝是干净的，没有半写**。<br>→ L-02 的说法 **成立**。 |
| **C) 身份含 blast radius**（本包建议） | `id(p1)=inval_1cf16e15…` / `id(p2)=inval_4d7ec80e…`（变宽 ⇒ 新身份），`record(p2)` **接受**，`records/events = (2, 2)`，**无硬错误**。 |

**本包的建议（若裁决为「应当折叠」）**：身份取
`sha256(source_evidence_id \| reason \| sorted(claims) \| sorted(gates))`，即**场景 C**。理由：

- 真正的重试（payload 完全相同）→ **折叠** ✔（场景 A 的性质保留）
- 事实**演化了**（blast radius 变宽/变窄）→ **新事实**，而**不是**一个会挡住后续工作的硬错误 ✔
- 对比 `sha256(evidence \| reason)`：那会把「blast radius 后来变宽」这种**合法演化**变成
  `InvalidationContractError`（场景 B），**把正常演化当成冲突**；而 C 里它只是新事实。
- 代价：`record()` 的冲突守卫在 C 下几乎不可达（同 id ⇒ 同内容，因为 id 由内容派生），
  它退化为**带外防御**而非实时冲突检测器——这一点如实写明。

> **本包不自行实施 C**：team-lead 已裁决「是否折叠」属**语义问题**、须老板拍板；
> 机制已由 L-02 备好，裁决落地后本包**一行**即可接上（传 `propagation_id=...` 并同步测试预期）。
> 上面的实测就是把裁决建立在**量过的事实**上，而不是推测上。
