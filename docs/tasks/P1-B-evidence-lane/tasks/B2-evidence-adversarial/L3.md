# P1-B2 Task-local L3

## State

```text
draft -> implemented -> tested -> handed-off -> integrated
```

## Evidence admission

- A candidate locator is required and must contain non-whitespace text.
- Missing locator returns `blocked` and appends a diagnostic event without
  writing an EvidenceItem.
- Direct formal evidence admission through EvidenceService also rejects a
  missing locator.
- Duplicate and conflict behavior from B1 remains unchanged.

## Evidence eligibility

- Invalidation remains an auditable status; it does not delete the evidence.
- `valid_only=True` resolution excludes invalidated evidence.
- `metadata.expires_at` is optional ISO-8601 text with a timezone.
- Past expiry, malformed expiry, and timezone-less expiry are invalid.
- Future expiry is valid.
- Expired or invalidated items cannot satisfy readiness or claim bindings.

## Benchmark and readiness rules

- BenchmarkAdvisor returns only concrete non-empty reading-card methods as
  baselines. It does not invent a comparator placeholder.
- An empty concrete baseline blocks readiness.
- Empty metrics or required-material entries also do not satisfy readiness.
- Any observed benchmark summary or `planned_only=False` breaks the
  planned-only guard and blocks readiness.

## Section validation rules

- Validation uses the readiness-resolved valid evidence IDs as the allowed
  evidence set.
- A draft claim bound to an invalid, expired, or out-of-plan evidence ID is
  `revise`, never `verified`.
- Existing B1 structure, profile, claim, plan, and section checks remain in
  force.
- A small allowlist of result-like metric phrases with numeric values is
  reported as `revise`. Evidence IDs, page numbers, years, and ordinary plan
  counts are not treated as result claims by this rule.
- Blocked readiness still short-circuits compose before draft/validation, as
  accepted in B1.

## Fixture policy

All B2 fixtures are offline and synthetic. They use fixed expiry timestamps,
`example.invalid` sources, and no real paper or experiment output.

## Boundary and rollback

No shared contract or project ledger is changed. If a shared change becomes
necessary, stop and request an integration-lane decision. Rollback removes
the B2 source/test/docs changes and leaves B1 behavior and records intact.
