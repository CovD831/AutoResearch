# B4 Task-local L3: Reader / Writer Ports

## State

```text
draft -> implemented -> tested -> handed-off -> integrated
```

Current state is `handed-off`. `integrated` requires the owner to create the PR
and merge it into the upstream mainline.

## Data shape

- `ReaderRequest` carries a request id, project id, a `PaperRecord`, and an
  optional question. `ReaderResult` carries the adapter kind, a typed
  `ReadingCard`, and an `EvidenceCandidate`.
- `WriterRequest` carries a request id, project id, a `SectionPlan`, reading
  cards, profile id, and benchmark plan id. `WriterResult` carries the adapter
  kind and a typed `SectionDraft`.
- `StructuredReadingPayload` / `StructuredDraftPayload` are the normalised
  outputs expected from off-port LLM/external capabilities. They are inputs to
  the structured adapters, never direct store records.
- `ClaimBinding` records, per claim, its bound evidence ids, the binding status
  (`bound` / `partial` / `unbound`), and the missing or invalid ids.
- `ParityReport` aggregates per-adapter rows with schema validity, claim count,
  bound count, binding rate, and gate compliance.

## Rules

1. Three adapters exist for each role: `native` (deterministic), `llm`, and
   `external`. Distinct implementations may differ in wording but must produce
   the same typed schema.
2. Native adapters are the deterministic oracle and fallback and never attempt
   a network call.
3. Structured adapters are transport-neutral: they wrap an already-normalised
   payload and never perform I/O or write records.
4. Non-native output always stays a candidate: a reading result carries an
   `EvidenceCandidate` and no adapter calls `EvidenceService.add` or writes an
   evidence record directly. Only `admit_candidate` may promote it.
5. Claim binding is 100% evidence: a claim with any missing or invalid
   evidence id is `partial`; a claim with no mapped evidence is `unbound`.
   Unbound/partial claims are never treated as supported.
6. Gate compliance fails closed: a planned-only draft reporting an observed
   result fails; an unbound/partial claim not listed in `unresolved_gaps` fails;
   a claim bound to evidence absent from `draft.evidence_ids` fails.
7. `completed_empty` upstream material is treated as material-missing by
   consumers and never re-invented as a result (see `docs/coord/empty-result-ruling.md`).
8. Parity is contract-level (schema, claim binding, gate compliance, planned-only)
   and never compares surface text.

## Fixture policy

Fixtures and payloads are synthetic, offline, and use `example.invalid` sources.
No real-paper retrieval, real model response, or observed experiment result is
included.

## Known limits

- The LLM/external adapters wrap supplied payloads; they do not implement live
  provider, MCP, or recipe wiring. That integration belongs to O12 ProviderLane
  and A4 capability adapters.
- B4 does not modify `reader_service.py`, `writing_service.py`, shared
  `contracts.py`, or any A-lane path.
- Owner integration review (2026-09-10, PR #13 → owner integration): the
  invisible-lineage gate check is constructed self-consistent for structured
  adapters (their `draft.evidence_ids` is derived from `claim_evidence_map`), so it only bites
  on the native path — consumers (A5/I4/B7) must not rely on it to catch
  structured lineage fabrication. The orphan-map-key gap was fixed at
  integration (gate now fails closed on map keys absent from claims).
- `review_ready=True` from B4 adapters means "draft-level completeness", not
  the mainline `readiness != BLOCKED` semantics (`writing_service.py:464`).
  Wiring (I line) must recompute or map explicitly.
- `compare_writer_parity` PASS carries no binding-rate floor; the "100%
  binding" guarantee is enforced by `gate_compliance` (unbound must be
  explicitly unresolved), not by a parity threshold.
